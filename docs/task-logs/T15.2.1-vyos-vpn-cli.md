## 2. 진행 방식

1. VyOS 1.4의 CLI, tunnel, site-to-site IPsec, static route 공식 문서를 확인했다.
2. 기존 IOS 파서에 서로 다른 문법을 섞는 대신 Router마다 CLI 형식을 선택하게 했다.
3. flat candidate tree를 CLI 세션에만 보관한다. commit 시 기존 물리/GRE/정적 경로/IPsec 모델로 컴파일하고 reducer의 공통 문서 검증을 통과해야 한 번에 교체한다.
4. IPsec 그룹과 PSK 인증 ID를 교육 정책 검사에 연결했다. 실제 암호화·IKE를 추가하지 않는다.
5. 엔진 회귀 테스트, 화면 렌더·JSON·안내서 명령 실행 테스트, 새 Chrome 탭에서 실제 입력을 검증했다.

### 주요 결정

| 결정 | 이유 |
|---|---|
| CLI 형식은 IOS/VyOS 선택 | 기존 실습과 팀원 PC/Switch 작업을 유지 |
| candidate는 Session, 적용된 tree는 Document | 미적용 입력은 JSON에 넣지 않고 적용 설정은 왕복 가능 |
| stale candidate commit 거절 | 다른 편집 경로의 새 설정을 덮어쓰지 않음 |
| 물리 포트 eth0~3, 터널 tun0~3을 내부 포트로 대응 | 케이블·라우팅 엔진 재사용 |
| 자동 결정적 SPI, 기존 수동 SPI 보존 | VyOS CLI에 없는 수동 SPI 명령을 만들지 않음 |
| PSK·ID·IKE/ESP 정책 불일치 거절 | 사용자 선택인 교육용 IPsec 모델에 설정을 실제 연결 |
| VyOS disable 정책은 비활성화 후 일반 경로 허용 | VPN을 끄는 것과 일반 라우팅 실패를 구분 |
| admin 상태만 변경 시 SA sequence 유지 | 같은 SPI에서 번호 초기화로 발생하는 중복 거절 방지 |
| save는 미지원, 내보내기/가져오기 사용 | 실제 영구 저장을 구현한 것처럼 성공 응답하지 않음 |

## 4. 결과와 검증

- 엔진의 새 VyOS 시나리오: GRE/IPsec 양방향 PC ping TTL126, Router ping 4/4, 캡슐화 trace, commit 원자성, 누락 설정, 미사용 그룹 오타, PSK/알고리즘/ID 불일치, disable/복구, 일반 라우팅 전환, stale candidate, IOS 전환, 명령·JSON 왕복, 미지원 문법, 도움말.
- 웹 테스트: VyOS 선택 표시, 전용 mode radio 숨김, 안내서의 R1/R2 명령 블록을 그대로 실행해 양방향 통신.
- Chrome `http://127.0.0.1:5175/?lab=ipsec`: R1/R2의 `configure`, `commit`, `exit`, R1 SA 조회 확인. PC_A `ping -n 1 192.168.2.10` 결과 `bytes=32 time=16ms TTL=126`, 손실 0%.
- 1차 회귀 검사에서 기존 interface/set-admin의 생략 포트를 채우는 동작 변화가 발견되어, 원래 문서 형태를 유지하도록 수정했다.

## 6. 계획과 달라진 점

기존 프로젝트 계획 문서는 수정하지 않았다. 사용자 요청에 따라 IOS 스타일의 PING9 전용 VPN 명령만 제공하던 상태에서, VyOS 1.4 지원 subset을 추가했다. 기존 IOS 흐름은 호환용이다.

실제 IKE 교환·재협상·암호화·인증 코드는 없다. IKE lifetime은 설정값만 보관하고, ESP lifetime은 가상 시간의 교육용 SA 만료에 적용한다. 알고리즘 이름은 정확 일치 검사이며 실제 제안 협상이 아니다. 조회 출력은 PING9 형식이다. 전체 VyOS OS 호환, connection-type, VTI, NAT-T, 인증서, IPv6, GRE+IPsec, SSL VPN은 범위 밖이다.
