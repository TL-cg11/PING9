## 1. 목표와 완료 기준

iptables를 실습할 수 있게 한다. 2026-11-16에 담당(SDY)이 "기존 장비(PC나 Router)에 얹지 않고 **별도 장비**로 만든다. 아이콘은 임시로 넣고 다른 팀원이 바꾼다"고 정했다. 그 전에 어느 장비에 얹기로 했는지의 기록을 저장소 문서, PR, Notion에서 찾았으나 없었다.

- [x] 장비 목록에서 Firewall을 끌어 놓을 수 있다. 이름은 `FW1`부터, 포트는 4개(`Ethernet0`~`Ethernet3`, 콘솔에서는 `eth0`~`eth3`)
- [x] Firewall은 인터페이스 사이에서 IPv4를 전달한다 (직접 연결, Static route). 자신에게 온 ping에 답하고 콘솔에서 ping을 보낸다
- [x] 콘솔은 Linux다: `ip addr`, `ip link`, `ip route`, `ip neigh`, `ping`, `iptables`, `help`
- [x] `iptables`로 filter 테이블의 INPUT, FORWARD, OUTPUT 체인에 규칙을 넣고(`-A`, `-I`), 지우고(`-D`, `-F`), 기본 정책을 바꾸고(`-P`), 본다(`-L`, `-S`)
- [x] 규칙의 조건: `-p icmp|tcp|udp|all`, `-s`, `-d`, `-i`, `-o`, `--icmp-type`, `--sport`, `--dport`. 대상: `ACCEPT`, `DROP`, `REJECT`
- [x] 규칙이 실제로 패킷을 거른다. 막힌 패킷의 추적에 어느 체인의 몇 번 규칙(또는 기본 정책)이 막았는지 남고, 시뮬레이션 모드의 "실패한 이유"에 보인다 (Story 14.3)
- [x] 규칙은 토폴로지에 저장된다. 내보냈다가 가져와도 그대로다
- [x] 속성 패널에 인터페이스 상태, 라우팅 테이블, 체인별 기본 정책과 규칙이 보인다
- [x] 공통 완료 조건: lint, 타입 검사, 단위 테스트, 빌드 (4절)
- [ ] 리뷰 — 팀원 검토 없이 병합했다 (6절)

## 2. 진행 방식

1. 기록을 찾았다. 계획 문서에는 Firewall이 "3차의 별도 장비, 무상태 패킷 필터(F1)"로만 있고(02 문서 2.5절, 04 문서 4.10절), 01 문서 1.4절은 "시뮬레이션에서는 실제 iptables를 쓰지 않고 패킷 필터 규칙 모델을 직접 구현한다"고 적었다. "PC냐 Router냐"는 어디에도 없어 담당에게 물었고, 별도 장비로 정해졌다.
2. 장비 종류 하나가 `shared`(문서 형태, 검증), `engine`(reducer, 모델, 런타임, 콘솔), `web`(목록, 아이콘, 패널, 문구)에 어떻게 걸려 있는지 읽었다. 종류로 갈라지는 곳은 대부분 `Record<DeviceKind, …>`와 `switch`라서, 종류를 더한 뒤 타입 검사가 빠진 곳을 알려 줬다.
3. `shared` → `engine` → `web` 순서로 넣었다. 단계마다 타입 검사와 그 패키지의 테스트를 돌렸다.
4. 엔진은 실습 토폴로지(PC1 — eth0 [FW1] eth1 — PC2)를 공개 인터페이스(`createSimulator`)로만 만드는 테스트로 확인했다.
5. 개발 서버를 띄워 브라우저에서 같은 실습을 손으로 했다 (4절).
6. 독립 검토(읽기 전용)를 돌려 나온 것을 고쳤다 (4절).

### 주요 결정

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| Firewall은 **전달하는 L3 장비**다. Router처럼 인터페이스마다 IP를 주고 그 사이를 전달한다 | 지나가는 트래픽을 걸러야 방화벽 실습이 된다 (FORWARD 체인). 02 문서 F1도 "인터페이스 방향별 규칙"이다 | 선 사이에 끼우는 L2 투명 방화벽: 인터페이스 방향 규칙과 INPUT·OUTPUT이 어색해진다 |
| 콘솔은 **Linux**다 (`root@FW1:~#`). IOS 모드가 없다 | iptables는 Linux 명령이다. Linux PC 콘솔(T0.7)과 같은 명령(`ip addr add … dev eth0`)을 쓴다 | IOS 콘솔에 `iptables`만 얹기: 실제에 없는 조합이다 |
| 필터는 **무상태**다. `-m state`, `conntrack`은 없다 | 02 문서가 F1(무상태)을 3차, F2(상태 추적)를 3차 이후로 나눴다. 응답이 돌아오지 못해 막히는 것 자체가 배울 거리다 | 상태 추적: 연결 테이블과 그 표시가 따로 필요하다 |
| filter 테이블과 기본 체인 셋만. `-t nat`, 사용자 체인, `!` 부정, `LOG`는 "PING9에 없는 기능"으로 알린다 | NAT는 2차(E9)의 일이다. 없는 것을 조용히 받아 넘기면 규칙이 동작하는 줄 안다 | 모르는 옵션을 무시하고 받기 |
| `-p tcp`·`-p udp`와 `--sport`·`--dport`는 받아서 저장하고 보인다. 지금 PING9의 패킷은 ICMP뿐이라 맞는 패킷이 없다 | 교재의 규칙(`-p tcp --dport 22 -j ACCEPT` 뒤에 `-P INPUT DROP`)을 그대로 칠 수 있고, 그 결과(ping이 막힘)도 실제와 같다 | ICMP만 받기: 흔한 규칙의 첫 줄에서 오류가 난다 |
| 인터페이스와 Static route는 Router와 **같은 Command**(`interface/set-ip` 등)를 쓴다. `reducer.ts`에서 장비가 Firewall이면 Firewall 처리기로 보낸다 (`orFirewall`) | Command의 뜻이 같다. Router의 처리기 파일은 고치지 않아, 열려 있는 [PR #63](https://github.com/TL-cg11/PING9/pull/63)(Router의 VPN)과 겹치는 줄이 적다 | `firewall/set-interface-ip`처럼 Command를 따로 만들기. Router 처리기 안에서 종류를 가르기 |
| 필터 규칙은 `firewall/add-rule`, `remove-rule`, `flush-rules`, `set-policy` 네 Command다. 규칙 번호는 iptables처럼 1부터다 | Document를 바꾸는 길은 Command 하나다 (AD-3) | 콘솔이 구성을 직접 바꾸기 |
| 모델(`FirewallModel`)은 Router 모델을 고치지 않고 **따로** 썼다. 경로 조회(`lookupRoute`)와 ARP 모듈만 같이 쓴다 | PC, Switch, Router 모델이 모두 장비별로 따로 있다. Router 모델은 PR #63이 크게 고치는 중이다 | Router 모델을 일반화해 필터 훅을 넣기 |
| `iptables` 줄은 명령 정의(cli/ios)의 자리 맞추기로 읽지 않고 **직접 읽는다** (`cli/firewall/iptables.ts`) | 옵션의 순서가 자유롭다. PC의 `echo`(T0.19)가 같은 방식의 예외다 | 옵션 순서의 조합마다 명령 정의 만들기 |
| 필터를 거는 자리: INPUT은 자기 주소로 온 패킷, FORWARD는 경로와 TTL을 본 **뒤**, OUTPUT은 이 장비가 만든 패킷(ping 요청·응답, ICMP 오류) | 실제 Linux의 순서다 (TTL 만료와 경로 없음은 FORWARD 훅보다 먼저 판정된다) | 받자마자 한 번에 거르기 |
| `REJECT`는 보낸 쪽에 ICMP 도달 불가를 돌려준다. OUTPUT의 `REJECT`는 `DROP`처럼 폐기만 기록한다 | PING9의 ICMP 오류는 도달 불가와 TTL 만료 둘뿐이다. OUTPUT에서는 실제로 프로그램에 오류가 돌아가는데 그 표시는 없다 | OUTPUT `REJECT`에 맞는 콘솔 문구 만들기 |
| 폐기 사유는 `FIREWALL_BLOCKED` 하나. params에 체인, 대상, 규칙 번호(기본 정책이면 없음) | Story 14.3. 문구는 web이 만든다 (AD-14) | 체인마다 사유 코드 나누기 |
| 포트 이름은 `Ethernet0`~`Ethernet3`. 콘솔에서만 `eth0`~`eth3` | PC가 그렇게 한다 (`Ethernet0` ↔ `eth0`). 화면의 줄임 표기(`Eth0`)를 그대로 쓴다 | 문서에 `eth0`을 저장: 포트 이름 규칙(AD-9)과 줄임 표기에 예외가 생긴다 |
| 인터페이스는 처음부터 켜져 있다 | Linux 장비다 (PC와 같다). Router의 "설정 전에는 꺼짐"(FR-17)은 IOS의 규칙이다 | Router처럼 꺼진 채로 시작 |
| 규칙은 **토폴로지에 저장**된다 | 실제 iptables는 재부팅하면 사라지지만, PC의 `ip addr add`도 저장된다 (T0.7의 같은 결정) | 런타임에만 두기: 내보내기에 빠진다 |
| 아이콘은 벽돌 벽과 불꽃. **임시**다 | 담당의 지시. 팀원이 바꾼다 | — |
| 속성 패널의 규칙은 보기만 한다. 새 CSS는 한 줄(긴 규칙의 줄바꿈)이고 나머지는 라우팅 테이블의 클래스를 쓴다 | 시안에 없는 화면을 새로 그리지 않는다. 규칙을 바꾸는 곳은 콘솔이다 | 패널에서 규칙 편집 |

### 브라우저에서 직접 (개발 서버, 1280×800)

1. 장비 목록의 Firewall을 캔버스로 끌어 놓음 → `FW1`, 벽돌 벽 아이콘. PC 둘을 놓고 케이블 도구로 PC1—FW1(`Ethernet0`), PC2—FW1(`Ethernet1`)을 이음. 포트 고르는 창에 `Ethernet0`~`Ethernet3`이 나오고, 쓴 포트는 다음에 빠진다.
2. FW1을 두 번 눌러 터미널을 엶 → 제목 줄에 `Firewall`, 프롬프트 `root@FW1:~#`.
3. `ip addr add 10.0.1.1/24 dev eth0`, `ip addr add 10.0.2.1/24 dev eth1` → 속성 패널의 라우팅 테이블에 `C 10.0.1.0/24 직접 Eth0`, `C 10.0.2.0/24 직접 Eth1`.
4. `iptables -A FORWARD -s 10.0.1.0/24 -p icmp --icmp-type echo-request -j DROP` → 속성 패널의 FORWARD 아래에 `1 -s 10.0.1.0/24 -p icmp -m icmp --icmp-type 8 -j DROP`. `iptables -L FORWARD -n --line-numbers`가 표로 나온다.
5. `iptables -A INPUT -m state --state NEW -j ACCEPT` → `-m` 아래에 `^`, "PING9의 iptables에는 없는 기능이에요: -m state. 쓸 수 있는 것은 iptables -h로 볼 수 있어요".
6. PC2에서 `ping -n 1 10.0.1.10` → `Reply from 10.0.1.10: bytes=32 time=8ms TTL=127`. PC1에서 `ping -n 1 10.0.2.10` → `Request timed out.`
7. 시뮬레이션 모드에서 같은 ping → 펭귄이 FW1까지 가서 멈춘다. 이벤트 탭의 "실패한 이유": "FW1의 FORWARD 체인 1번 규칙(DROP)이 이 패킷을 막았어요 / FW1에서 규칙을 확인하세요: `iptables -L FORWARD -n --line-numbers`". 이벤트 3번: "✕ FORWARD 체인의 1번 규칙(DROP)이 막아 버림".

PC의 속성 패널 입력란에 글자를 넣는 것은 자동 조작이 듣지 않아(창이 숨겨져 있었다) PC의 콘솔 `ipconfig <IP> <마스크> <게이트웨이>`로 주소를 넣었다. 패널 자체는 이 Task가 고치지 않았다.

## 7. 남은 일과 다음 Task에 전할 것

- **PR #63(VPN, VyOS CLI)과 겹친다.** 미리 합쳐 보니 4개 파일이 충돌한다 (4절). 이 Task가 먼저 들어가면 #63이 `main`을 받아 맞춰야 한다. 충돌하지 않는 파일도 여럿 함께 고쳤으니(`reducer.ts`, `runtime.ts`, `console.ts`, 속성 패널, 문구) 합친 뒤 `pnpm check`가 필요하다. #63이 Router에 넣는 터널·VPN은 Firewall에는 없다.
- Router의 `interface/set-ip`는 Firewall과 겹치는 주소를 알리지 않는다 (`reducer/router-interface-ip.ts`가 PC와 Router만 본다). Firewall과 PC 쪽에서 넣을 때는 알린다. Router 담당이 한 줄(`other.kind === "firewall"`)을 더하면 된다.
- 아이콘 교체 (`apps/web/src/components/device-icons.tsx`의 `FireWall`). 테스트는 그림이 다른 장비와 다른지만 본다.
- 실제 iptables와 다른 점 (콘솔의 `iptables -h`와 `help`에 쓰는 법이 있다):
  - `-v`에 패킷·바이트 수 칸이 없다. 규칙별로 세지 않는다.
  - OUTPUT에서 막힌 ping은 `Operation not permitted`가 아니라 응답 없음(100% loss)으로 보인다.
  - 자기 주소와 `127.x`로 보내는 ping은 링크도 필터도 지나지 않는다 (`-i lo`가 없다).
  - 인터페이스 하나에 주소 하나다. `ip addr add`를 다시 치면 바뀐다.
  - 닿지 않는 다음 홉의 Static route도 받는다. 경로 표에는 닿을 때만 보인다 (Router와 같다).
  - Firewall 콘솔에는 `traceroute`, `ifconfig`, `route -n`, `iptables-save`가 없다.
- 화면의 포트 표기는 `Eth0`이고 콘솔은 `eth0`이다. Linux PC와 같은 차이다.
- Router의 속성 패널이 다음 홉의 주인 이름을 찾을 때(`router-inspector.tsx`의 `ownerName`) Firewall의 주소는 보지 않는다. RIP 경로의 표시에만 쓰여 Firewall(RIP 없음)과는 지금 만나지 않는다.
- 실패한 이유의 안내 명령이 IOS의 것이다: `IF_DOWN`은 `no shutdown`, `NO_ROUTE`는 `ip route <네트워크> <마스크> <다음 주소>`, `NO_IP`는 "상세 정보에서 IP를 설정". Firewall에서는 `ip link set … up`, `ip route add … via …`, `ip addr add … dev …`가 맞다. 사유의 params에 장비 종류가 없어 문구가 가르지 못한다 (Linux PC의 `IF_DOWN`도 같다). params에 종류를 넣을지는 팀이 정할 일이다.
- `iptables` 해석이 실제보다 느슨하거나 좁은 곳: 같은 옵션을 두 번 쓰면 뒤의 것을 쓴다(실제는 오류). `--dport=80`, `-ptcp`처럼 붙여 쓴 값과 `-V`, `-x`는 받지 않는다. `ipt -L`처럼 줄여 치면 `iptables`의 줄임으로 읽혀 `-L`이 모르는 단어라는 오류가 난다.
- Firewall의 `ip` 명령은 Linux PC 콘솔과 같은 범위다. `ip address`, `ip route list`, `ip neighbor`, `ping -c1`은 받지 않는다.
- NAT(`-t nat`)는 2차 E9, 상태 추적(`-m state`)은 F2에서 다룬다. 둘 다 지금은 "PING9에 없는 기능"으로 알린다.
