## 2. 진행 방식

테스트를 먼저 쓰고(10개 실패, 파일 하나는 모듈이 없어 실패) 구현했다.

1. **목록의 글 형태** (`vlan-list.ts`): 읽기(`parseVlanList`)와 쓰기(`formatVlanList`).
2. **reducer**: `switchport/set-allowed-vlans`. 형태 확인 → 정렬과 합치기 → 64개 한도.
3. **명령어**: 목록은 `customParam`으로 읽는다. 틀린 목록은 해석 단계에서 위치와 함께 거부된다.
4. **전달 규칙**: `classify`와 `egress`의 trunk 분기.
5. **화면**: `linkVlan`에 trunk, 캔버스의 선·표시·끝의 글, 속성 패널의 trunk 줄.

### 주요 결정

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| native VLAN은 1로 고정 (태그 없는 프레임은 VLAN 1) | 설계 6.2절. 바꾸는 기능은 2차 범위다 | `switchport trunk native vlan` |
| 빈 허용 목록(`none`)은 그대로 저장, 전부 허용은 기본값이라 저장하지 않음 | "없음 = 전부 허용"과 "빈 배열 = 아무것도 허용하지 않음"은 다른 뜻이다 (설계 5.2절, 5.3절) | 빈 배열도 지움 |
| 합친 **뒤**의 범위 수로 한도를 봄 | `1,2,3,…,200`은 범위 하나다. 입력의 개수로 막으면 쓸 수 있는 목록을 거부한다 | 입력의 개수로 봄 |
| 목록의 수가 범위를 벗어나면 `INVALID_VLAN_ID`, 모양이 틀리면 `CLI_INVALID_VALUE` | 값 형식 오류는 `shared` 값 검증의 코드를 그대로 쓴다 (설계 7.3절) | 모두 `CLI_INVALID_VALUE` |
| `allowed vlan add`/`remove`는 넣지 않음 | 설계 14절 6번 | — |
| 화면의 허용 목록 글은 화면에서 만든다 (`formatAllowedVlans`: `10, 20`, `전체`, `없음`) | 표현이다. engine의 글(`10,20`, `all`)은 명령어로 다시 넣을 수 있는 형태라 따로다 | engine의 글을 그대로 씀 |
| 한쪽 끝만 trunk여도 trunk 선으로 그림 | 설계 8.1절. 설정이 어긋난 것이 눈에 보인다 | 양쪽 다 trunk일 때만 |

## 6. 계획과 달라진 점

- **통합 테스트 "Switch 2대의 같은 VLAN끼리 ping"은 하지 않았다.** kernel과 ping이 없어 `switchForward`의 장면 테스트로 대신했다.
- **시안의 빨간 경고 줄("trunk Fa0/8에 VLAN 10 허용 없음")은 넣지 않았다.** engine이 실패 원인을 계산해야 나오는 것이다 (설계 8.1절).

### 검토에서 나온 것 (2026-11-06)

- **`switchport trunk allowed vlan add <목록>`을 넣었다.** 설계 14절 6번은 `add`/`remove`를 넣지 않는다고 했지만, `show running-config`가 긴 목록을 여러 줄로 나눠 쓰려면 `add`가 필요하다 (T3.4.1 기록 참조). 지금 목록에 더한 것을 `switchport/set-allowed-vlans`로 보내고, 합치기는 reducer가 한다. `remove`는 넣지 않았다.
- **캔버스 표시의 한계 (고치지 않음)**: 한 Switch에서 같은 쪽으로 나가는 trunk가 둘이면 끝의 글이 겹친다 (글의 자리가 노드에서 고정 거리다). 끝의 글은 viewBox 계산에 들어가지 않아 오른쪽 가장자리에서 잘릴 수 있다. Switch끼리 access 포트로 이었는데 양쪽 VLAN이 다르면 첫 끝의 VLAN만 보인다. 브라우저에서 확인하지 않았다.
