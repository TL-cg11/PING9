## 2. 진행 방식

1. 03 문서 3.4절, 규칙 문서의 AD-3·AD-6·AD-7·AD-8·AD-14·AD-16, 02 문서의 FR-38·FR-42·FR-43·FR-44·FR-47, 05 문서 5.5절의 한도를 읽었다.
2. 문서가 형태를 정해 둔 것은 그대로 옮겼다: `Snapshot`, `DispatchResult`, `ConsoleResult`, `ConsoleLine`, `Trace`, `TraceEvent`, Document의 예시, Command 18개, 포트 상태 4개, 폐기 사유 11개.
3. 문서에 이름만 있고 내용이 없는 것은 초안을 정했다: `DeviceView`, `FrameSnapshot`, `TraceSummary`, `HelpEntry`, 오류·알림·이벤트 설명 코드의 목록과 코드별 `params`.
4. 범위는 [PC 2대 계획](../project-plan/06-two-pc-ping-plan.md)의 일부가 아니라 **MVP 전체**(Switch, Router 구성과 모든 Command)로 잡았다. 타입만 있고 동작이 없어 비용이 작고, 나중에 타입을 늘릴 때마다 세 사람이 다시 맞추는 일을 줄인다.

### 주요 결정

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| 코드와 `params`를 한 쌍의 타입으로 묶음. `code`로 좁히면 `params`의 타입이 정해짐 | 문서는 `params: object`로만 적었음. 그대로 두면 화면이 문구를 만들 때 `params`의 이름을 추측해야 함 (AD-14가 막으려는 것) | `params: object` 그대로 |
| 코드 목록은 TypeScript `enum`이 아니라 문자열 묶음 타입 + 목록 상수 | JSON에 그대로 실리고, 목록에서 빠뜨리면 타입 오류가 남 (`satisfies Record<Code, true>`) | `enum` |
| 모든 속성과 배열을 `readonly`로 | 경계를 오가는 값은 변경 불가능해야 함 (AD-16). 화면이 스냅샷을 제자리에서 고치면 타입 오류 | 주석으로만 약속 |
| 폐기 이벤트의 `reason.code`는 폐기 사유와 같은 값 | 폐기 사유마다 문구에 넣을 값(장비, 포트, 주소)이 다름. 설명 코드와 폐기 사유를 따로 두면 같은 내용을 두 번 적게 됨 | 설명 코드 `DROPPED` 하나 + `dropReason` |
| `DeviceView`에는 engine이 계산한 값과 실행 중 상태만 담음 (포트 상태, 테이블) | IP나 VLAN 목록은 Document에 있음. 같은 값을 두 곳에 두지 않음 (AD-4) | 구성 값도 view에 복사 |
| `pc/set-ip`의 `ip`가 `null`이면 IP를 지움 | "IP를 지우고 ping하면 실패 사유가 표시된다"(M2 확인 항목)를 하려면 지우는 방법이 필요한데 Command 목록에 `pc/clear-ip`가 없음 | `pc/clear-ip`를 새로 추가 |
| 한도 상수는 `LIMITS` 객체 하나 | 한도를 찾을 곳이 하나 | 상수를 낱개로 |

## 3. 변경 내용

## 4. 결과와 검증

```text
> pnpm --filter @ping9/shared typecheck      [exit 0]
> pnpm --filter @ping9/shared test
  src/codes.test.ts   11 passed
```

- 수용 기준의 타입 목록(`TopologyDocument`, `PortRef`, `Command`, `DispatchResult`, `Notice`, `Snapshot`, `DeviceView`, `PortStatus`, `ConsoleResult`, `ConsoleLine`, `Trace`, `TraceEvent`, 코드 열거형과 `params`, 한도 상수)이 모두 `@ping9/shared`에서 import됩니다. engine, web, api가 실제로 가져다 쓰고 타입 검사를 통과합니다.
- 컴파일 테스트: `errorInfo("PORT_IN_USE", { device: "d" })`처럼 `params`의 이름이 틀리거나 없는 코드를 쓰면 타입 오류가 나는 것을 `@ts-expect-error`로 확인합니다.
- 예시 값이 타입에 맞는지는 [T1.2.3](T1.2.3-example-data.md)의 예시 자료가 `TopologyDocument`, `Trace`, `Snapshot`, `ConsoleResult` 타입으로 선언되어 타입 검사를 통과하는 것으로 확인됩니다.
