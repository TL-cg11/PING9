## 2. 진행 방식

1. 설계안(팀 합의 전)의 결정 8가지를 사용자와 정했다: 교환마다 처음부터 배우기, UDP는 포트 두 개만, Request 먼저, triggered update는 바뀐 경로만, poison reverse 없음, Trace 층 `RIP` 새로, 구성이 바뀌면 배운 경로를 지움, T11.1.1 브랜치에서 시작.
2. 공통: 프레임에 `udp`, `rip`. 층 `RIP`. 이벤트 코드 6개와 폐기 사유 `RIP_SOURCE_NOT_ON_LINK`. Trace 검증.
3. `RipModule`(`devices/router/rip.ts`): ARP 모듈처럼 `RouterModel`에 붙는다. 보내기·받기·배우기·split horizon·triggered update·25개씩 나누기.
4. 연결: `RouterModel`이 RIP 프레임을 모듈로 넘기고, 패킷 전달에 배운 경로를 쓴다. `Runtime.exchangeRoutes`, `routingTable`. 화면의 Router 테이블과 `show ip route`가 Runtime의 테이블을 쓴다.
5. 예시 토폴로지 `threeRouterRipDocument`(`shared/examples/rip-lab.ts`)와 테스트 16개.

### 경로 교환 1회의 흐름

```
시작: RIP Router마다 배운 경로를 지우고, 보낼 인터페이스마다 Request (224.0.0.9)
      + 30ms(가상) 뒤 정기 갱신 타이머
Request를 받음 → 요청한 Router에게 전체 경로 (split horizon)
Response를 받음 → metric < 16이고 더 좋으면 배움 → 바뀐 경로만 모든 보낼 인터페이스로 (triggered update)
타이머 → 보낼 인터페이스마다 전체 경로 (정기 갱신 1회)
큐가 빔 → 끝 (status: success)
```

### 주요 결정

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| 교환마다 처음부터 배움 | 끊긴 링크 너머의 경로가 저절로 사라진다. 옛 정보가 없어 count-to-infinity가 없다. PING9는 시간이 흐르지 않아 180초·240초 타이머를 쓸 수 없다 | 배운 경로를 두고 타이머로 지움 |
| split horizon만, poison reverse 없음 | IOS 기본값. 처음부터 배우므로 꼬일 일이 없고, 재생에 의미 없는 패킷이 줄어든다 | 둘 다 |
| 보낼 때 metric +1, 받은 쪽은 그대로 씀. 직접 연결은 1로 보냄 | 실제 RIP의 패킷 값과 같다 (`[120/1]`은 바로 옆) | 받은 쪽이 +1 |
| 같은 metric을 다른 이웃에게 들으면 먼저 들은 것 | 사건 순서가 결정적이라 결과도 결정적이다 | ECMP |
| Request에 대한 Response는 요청한 Router의 MAC으로 바로 보냄 (ARP 없음) | 받은 프레임의 출발 MAC을 안다. ARP를 넣으면 재생에 RIP와 상관없는 프레임이 늘어난다 | 실제처럼 ARP 뒤 유니캐스트 |
| RIP를 켜지 않은 Router·참여하지 않는 인터페이스가 받은 RIP는 `NOT_FOR_ME` | 멀티캐스트 그룹에 없는 것과 같다. 정상 폐기라 실패의 원인으로 잡히지 않는다 (kernel과 화면이 `NOT_FOR_ME`만 정상 폐기로 본다) | 새 사유 `RIP_NOT_ENABLED_ON_PORT` (설계안) |
| 배운 경로는 나가는 인터페이스가 살아 있을 때만 테이블에 | 인터페이스를 끄면 다음 교환을 기다리지 않고 바로 빠진다 | 다음 교환까지 남김 |
| 멀티캐스트는 Switch 코드를 바꾸지 않음 | 멀티캐스트 MAC은 출발지로 배워지지 않아 지금도 flooding된다 (E11 결정 9) | Switch에 멀티캐스트 처리 추가 |

## 6. 계획과 달라진 점

- 계획(04 문서 4.9절)에는 E11의 Task 분해가 없다. `T11.2.2`는 이 작업에서 정한 ID다.
- 설계안과 달라진 점:
  - **정기 갱신 1회를 더했다.** 시작 30ms(가상) 뒤 각 Router가 전체 경로를 한 번 보낸다. Request만으로는 passive 인터페이스 너머의 경로를 듣지 못했다 (passive는 Request에 답하지 않고, 실제에서는 30초마다 오는 정기 갱신으로 듣는다).
  - 참여하지 않는 인터페이스로 온 RIP는 새 사유 대신 `NOT_FOR_ME`로 버린다 (2절 주요 결정).
  - Request에 대한 Response는 ARP 없이 요청한 Router의 MAC으로 보낸다.
  - 설계안은 받은 쪽이 metric에 1을 더한다고 적었지만, 보내는 쪽이 더한다 (결과는 같고 실제 패킷 값과 같다).
- `Simulator`에 `exchangeRoutes()`를 더했다 (공개 API).
