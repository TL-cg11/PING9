## 1. 목표와 완료 기준

T14.2.1의 Firewall은 `-p tcp --dport 80` 같은 규칙을 받지만, PING9의 패킷이 ICMP뿐이라 그 규칙에 맞는 패킷이 없었다. Packet Tracer의 서버(Services 탭)처럼 HTTP, DNS, NTP, FTP를 돌리는 장비와 그 요청을 보내는 명령이 있어야 시험할 수 있다.

담당의 결정(2026-11-16): **별도 장비를 만들지 않는다.** PC의 OS 고르기(Windows, Linux)에 **Server**를 하나 더 넣고, 그 PC가 서비스를 돌린다.

- [x] 속성 패널의 OS에서 Server를 고를 수 있다. 서버는 Linux 콘솔을 쓰고 그림이 다르다
- [x] 서버는 HTTP(tcp/80), DNS(udp/53), NTP(udp/123), FTP(tcp/21)를 돌린다. 처음에는 넷 다 켜져 있고, 패널의 스위치나 콘솔의 `systemctl`로 끄고 켠다
- [x] DNS가 답할 이름(A 레코드)을 패널에서 넣고 지운다
- [x] 모든 PC의 콘솔에서 요청을 보낸다: `curl`(HTTP, FTP), `nslookup <이름> <서버>`, Linux `ntpdate -q`, Windows `w32tm /stripchart /computer:<서버>`
- [x] 요청은 실제 패킷으로 오간다: TCP는 SYN → SYN-ACK → ACK로 연결을 맺고 요청과 응답을 주고받는다. UDP는 요청과 응답 한 번씩이다. Switch, Router, Firewall을 지난다
- [x] Firewall의 TCP·UDP 규칙(`-p`, `--sport`, `--dport`)이 이 패킷을 거른다. DROP은 시간 초과로, REJECT는 거절로 보인다
- [x] 듣는 서비스가 없는 포트는 거절한다 (TCP는 RST, UDP는 ICMP 도달 불가). 이유가 추적에 남는다 (`PORT_CLOSED`)
- [x] 시뮬레이션 모드에서 요청이 재생되고 이벤트 목록에 TCP·서비스 단계가 보인다
- [x] 공통 완료 조건: lint, 타입 검사, 단위 테스트, 빌드 (4절)
- [ ] 리뷰 — 팀원 검토 없이 병합했다 (6절)

## 2. 진행 방식

1. 처음에는 Packet Tracer처럼 별도 Server 장비로 설계를 잡았다. 코드를 고치기 전에 담당이 "PC의 OS 선택에 Server를 넣자"로 바꿨다.
2. OS 값이 쓰이는 곳을 모두 찾았다. PC의 콘솔 코드는 `os === "linux"`로 가르는 곳이 스무 군데가 넘어, OS 값에 `server`를 더하면 그 모두가 서버를 Windows로 다룬다. 그래서 **고른 종류**(`windows`, `linux`, `server`)와 **동작하는 OS**(`windows`, `linux`)를 나눴다: `osOf()`는 서버에 `linux`를 돌려주고, 기존 코드는 고치지 않았다.
3. `shared` → `engine` → `web` 순서로 넣었다. 단계마다 타입 검사와 그 패키지의 테스트를 돌렸다.
4. PC1 — Firewall(또는 Router, Switch) — 서버 토폴로지를 공개 인터페이스(`createSimulator`)로 만드는 테스트로 확인했다.
5. 개발 서버를 띄워 브라우저에서 같은 실습을 손으로 했다 (4절).
6. 독립 검토(읽기 전용)를 돌려 나온 것을 고쳤다 (4절).
7. 그 사이 `main`에 [PR #63](https://github.com/TL-cg11/PING9/pull/63)(VPN, VyOS CLI)과 [PR #64](https://github.com/TL-cg11/PING9/pull/64)가 들어와, `main`을 받아 9개 파일의 충돌을 풀었다 (4절).

### 주요 결정

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| 서버는 **PC의 종류**다. 문서에는 `os: "server"`로 저장한다 | 담당의 결정. 장비 종류, 모델, 콘솔, 설정 화면을 새로 만들지 않는다 | 별도 `server` 장비 (처음 설계) |
| 고른 종류(`PcOsChoice`)와 동작하는 OS(`OsKind`)를 나눴다. 서버는 Linux로 동작한다 | 기존 PC 코드의 `os === "linux"` 분기를 고치지 않아도 서버가 Linux 콘솔·TTL 64·`eth0`으로 동작한다 | `OsKind`에 `server`를 더하고 분기마다 고치기: PC 담당의 파일 여럿을 고쳐야 하고 빠뜨리면 조용히 Windows가 된다 |
| 서비스 구성은 `services`(켜 둔 목록)와 `dnsRecords` 칸. 서버인데 `services` 칸이 없으면 **넷 다 켜짐** | 종류를 Server로 바꾸면 바로 쓸 수 있다. 옛 문서는 그대로 읽힌다 | 서비스마다 켜짐 칸: 칸이 넷으로 늘고 기본값 규칙이 넷이다 |
| 종류를 Windows·Linux로 바꿔도 서비스 구성은 문서에 남는다. 서버가 아니면 듣지 않을 뿐이다 | 잠깐 바꿨다가 돌아와도 DNS 이름을 다시 넣지 않는다 | 종류를 바꿀 때 지우기 |
| TCP는 SYN, SYN-ACK, ACK, 요청, 응답의 다섯 프레임. **FIN, 순서 번호, 재전송은 없다** | 연결을 맺는 것과 방화벽이 어느 프레임을 막는지가 배울 거리다. 추적이 길어지지 않는다 | 연결 끊기까지: 프레임이 넷 더 늘고 화면이 길어진다 |
| 서버는 연결 상태를 기억하지 않는다. 요청이 오면 답한다 | 요청은 한 번에 하나다 | 연결 표 |
| 응용 계층은 첫 줄(`GET /`, `200 OK`)과 본문(`data`, 512자까지)만 | 이벤트 목록에 한 줄로 보인다 | HTTP 헤더, DNS 메시지 형식 |
| **이름 풀이는 없다.** `curl`은 IP 주소만 받고, 이름은 `nslookup <이름> <서버>`로 직접 묻는다 | PC에 DNS 서버 설정을 두는 것은 PC 담당의 범위이고 이 Task의 목적(방화벽 시험)에 필요 없다 | PC에 DNS 서버 칸 |
| FTP는 `curl ftp://<IP>/`로 쓴다. 제어 연결(21) 하나로 목록과 파일을 준다. 로그인, 데이터 연결(20, 수동 모드)은 없다 | 콘솔이 한 줄에 명령 하나라 `ftp>` 대화가 없다. 실제 curl도 FTP를 받는다 | 대화형 `ftp` |
| 웹 문서와 파일은 정해진 둘(`index.html`, `readme.txt`)이고 고칠 수 없다 | 방화벽 시험에는 "답이 온다"면 된다 | Packet Tracer의 File Manager |
| NTP는 계층(stratum 1)과 왕복 시간만 답한다 | 시뮬레이터에 벽시계가 없다 (가상 시간뿐) | 브라우저의 시각 쓰기: 결과가 실행마다 달라진다 (AD-5) |
| 닫힌 포트: TCP는 RST, UDP는 ICMP 도달 불가. 폐기 사유 `PORT_CLOSED` | 실제 동작이다. 실패한 이유에 "그 포트에서 듣는 서비스가 없어요"가 뜬다 | 조용히 버리기 |
| ICMP 오류에 막힌 패킷의 프로토콜과 목적지 포트를 담는다 (`original.protocol`, `destinationPort`). 이때 `sequence`는 0 | 보낸 PC가 어느 요청이 막혔는지 안다. ping의 오류(순번 1부터)와 섞이지 않는다 | TCP·UDP에는 ICMP 오류를 내지 않기: REJECT가 DROP과 같아 보인다 |
| 서비스 요청의 추적 요약은 `kind: "ping"`에 `service` 칸을 더한 것 | 화면의 추적 목록, 재생, 터미널의 줄 보이기가 그대로 동작한다 | 새 `kind`: web의 여러 곳을 고쳐야 한다 |
| Router와 Firewall이 전달할 때 TCP·UDP·응용 계층을 그대로 옮긴다 | 전에는 프레임을 ICMP만 실어 다시 만들어, TCP가 Router를 지나면 사라졌다 | — |
| Router·Firewall 자신의 주소로 온 TCP·UDP는 `PORT_CLOSED`로 남기고 ICMP 도달 불가로 답한다 | 게이트웨이 주소에 `nslookup`을 치는 것은 흔한 실수다. 이유 없이 4초를 기다리게 두지 않는다 | 조용히 버리기 (검토 전의 동작) |
| 서버의 콘솔은 Linux PC의 것에 `ss -tuln`, `systemctl start\|stop\|status`를 더한 것 | 실제 서버에서 쓰는 명령이다. `systemctl`은 패널의 스위치와 같은 Command를 낸다 (AD-3) | 서버 전용 콘솔 |
| 그림은 이글루에 장비 선반 간판. **임시**다 | Firewall처럼 팀원이 바꿀 수 있다 | — |
| 서비스 스위치와 DNS 칸은 포트 스위치(T0.14)와 IP 설정(T1.5.2)의 모양을 그대로 쓴다 | 시안에 없는 모양을 새로 그리지 않는다 | 새 디자인 |

### 브라우저에서 직접 (개발 서버, 1280×800. `main`을 받기 전의 코드로 했다)

1. PC 둘과 Firewall을 놓고 PC2의 OS에서 **Server**를 고름 → 그림이 바뀌고, 패널에 서비스 스위치 넷(켜짐)과 "DNS 이름" 구역이 생긴다. 포트 이름이 `eth0`이 된다.
2. 케이블을 잇고 주소를 넣음 (FW1 `ip addr add …`, 서버 `ip addr add 10.0.2.10/24 dev eth0`·`ip route add default via 10.0.2.1`, PC1 `ipconfig …`).
3. 서버에서 `ss -tuln` → `udp 53`, `udp 123`, `tcp 21`, `tcp 80`.
4. PC1(Windows)에서 `curl http://10.0.2.10/` → `<html><body><h1>PC2</h1><p>PING9 web server</p></body></html>`. `nslookup www.ping9.test 10.0.2.10` → `*** UnKnown can't find www.ping9.test: Non-existent domain`. `curl ftp://10.0.2.10/` → `index.html`, `readme.txt`.
5. FW1에서 `iptables -A FORWARD -p tcp --dport 80 -j DROP`.
6. 시뮬레이션 모드에서 `curl ftp://10.0.2.10/readme.txt` → 펭귄이 오간 뒤 `Files on PC2 are served over HTTP and FTP.` 이벤트 20개: "TCP 연결 요청(SYN)을 10.0.2.10로 보냄 (포트 21)" … "FTP 요청을 10.0.2.10로 보냄: RETR readme.txt" … "10.0.2.10의 FTP 응답을 받음: 226 Transfer complete". 추적 이름은 `PC1 → 10.0.2.10 (FTP)`.
7. `curl http://10.0.2.10/` → 펭귄이 FW1에서 멈추고 `curl: (28) Failed to connect to 10.0.2.10 port 80: Connection timed out`. 실패한 이유: "FW1의 FORWARD 체인 1번 규칙(DROP)이 이 패킷을 막았어요".

확인하다 고친 것: OS 고르기가 셋이 되면서 패널이 5px 넘쳐 가로 스크롤이 생겼다. 사이를 좁히고 줄바꿈을 허용했다.

`main`을 받은 뒤에 다시 띄워 짧게 봤다: Router를 놓으면 PR #63의 VPN 구역이 그대로 나오고, PC를 Server로 바꾸면 서비스 구역이 나온다. 서버 터미널에서 `curl 127.0.0.1`이 문서를 주고, `systemctl stop ftp` 뒤 `ss -tuln`에서 `tcp 21`이 빠지며 패널의 FTP 스위치가 꺼짐으로 바뀐다. 케이블을 이은 전체 실습은 합친 뒤에 다시 하지 않았다 (자동 테스트가 본다).

| # | 내용 | 처리 |
|---|---|---|
| 1 | DNS 이름이 길면(56자부터) 응답의 첫 줄이 64자를 넘어 추적이 형식 검사에 걸림 | 고침. 이름을 45자까지로 줄였다. 테스트 |

| 5 | 주소가 겹친 장비에 응답이 가면 그 장비가 요청으로 읽어 답함 | 고침. 클라이언트 포트로 온 것은 요청으로 읽지 않는다 |

### `main`과 합치기

`origin/main`(PR #63, #64)을 받으며 9개 파일이 충돌했다: `shared`의 `trace.ts`·`schema.ts`·`command.ts`·`index.ts`·`codes.test.ts`, `engine`의 `router-model.ts`, `web`의 `event-panel.tsx`·`steps.ts`·`editor.css`. 모두 양쪽의 것을 남겼다 (계층 목록에 `GRE`·`IPSEC`와 `TCP`·`UDP`·`APP`, 프레임 종류에 GRE·ESP와 TCP·UDP). 합친 뒤 위의 전체 검사가 통과했다.

## 6. 계획과 달라진 점

- **팀원 검토 없이 병합했다.** 담당의 요청이다.
- **계획에 없는 기능이다.** 02 문서의 범위에는 서버 장비도, TCP·HTTP·DNS·NTP·FTP도 없다 (UDP는 2차의 DHCP와 RIP에만 나온다). Firewall을 시험하려는 담당의 요청으로 넣었다.
- **PC 담당(yysong1249)의 영역을 고쳤다**: PC의 구성(`PcConfig`), OS 고르기, PC 모델, `ipv4-host.ts`, `pc-set-ip.ts`·`pc-set-os.ts`, PC 콘솔의 명령 목록(`os.ts`), 속성 패널. 기존 동작은 바꾸지 않았고 테스트가 그대로 통과한다. 확인이 필요하다.
- **Router 담당(ssunyoung2)의 `router-model.ts`를 고쳤다**: 전달할 때 계층 옮기기, 자기 주소로 온 TCP·UDP, ICMP 오류. ping과 GRE·IPsec의 동작은 그대로다.
- **`shared`에 더한 것은 팀 합의 전이다**: OS 값 `server`, Command 3개, 오류 4개, 이벤트 6개, 폐기 사유 `PORT_CLOSED`(FR-47의 표에 없다), 프레임의 `tcp`·`application`, 추적 계층 셋, 한도 `maxDnsRecords`(32).
- **T14.2.1의 기록이 바뀌었다**: 그 문서는 "`-p tcp` 규칙은 맞는 패킷이 없다"고 적었다. 이제 있다.

## 7. 남은 일과 다음 Task에 전할 것

- Router의 TCP·UDP 처리와 그 테스트는 `main`을 합친 커밋에 들어 있다 (기능 커밋이 아니다).
- 실제와 다른 점:
  - TCP에 연결 끊기(FIN), 순서 번호, 재전송이 없다. 서버는 연결 상태를 기억하지 않는다.
  - 요청은 한 번에 하나이고 클라이언트 포트는 늘 49152다.
  - 경로가 없어 돌아온 ICMP 도달 불가도 `curl`은 "Connection refused"로 보인다. PING9의 ICMP 오류는 도달 불가와 TTL 만료 둘뿐이라 "포트에 닿지 않음"과 "네트워크에 닿지 않음"을 가르지 못한다.
  - `curl`은 IP 주소만 받는다. HTTPS, `-I` 같은 옵션, 헤더는 없다.
  - FTP는 로그인과 데이터 연결이 없고 올리기(`STOR`)도 없다.
  - DNS는 A 레코드만. NTP는 시각을 주지 않는다.
  - Windows의 `w32tm` 출력에는 시각 칸이 없다. Windows `nslookup`은 거절당해도 "timed out" 문구가 바로 뜬다.
- **GRE·IPsec 터널은 ICMP만 싣는다** (PR #63의 설계). TCP·UDP를 터널로 보내면 Router가 `GRE_REJECTED`("미지원 payload")로 버린다. 터널 너머의 서버에는 `curl`이 닿지 않는다.
- Router와 Firewall의 콘솔에는 `curl`이 없다. Firewall의 OUTPUT 체인은 ping으로만 시험할 수 있다.
- 주소가 겹친 서버 둘이 있으면 연결과 요청이 서로 다른 서버로 갈 수 있다 (검토 6번).
- 웹 문서와 파일을 고치는 화면(Packet Tracer의 File Manager), PC의 DNS 서버 설정과 이름으로 `curl` 하기, HTTPS, DHCP·TFTP·SYSLOG·EMAIL 서비스는 하지 않았다.
- 서버 그림은 임시다 (`device-icons.tsx`의 `igloo-server`).
