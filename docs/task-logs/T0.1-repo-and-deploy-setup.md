- [x] 계획 문서가 저장소에 올라가 팀원이 받을 수 있다.
- [x] Task마다 기록 문서를 남기는 규칙과 템플릿이 있다.

## 2. 진행 방식

1. 폴더와 계획 문서를 읽고, 저장소에 넣을 것과 뺄 것을 나눴다.
2. `git init -b main`, 원격 `origin` 등록. 커밋 전에 토큰·키 형태의 문자열과 `.env` 파일을 검색해 없음을 확인했다.
3. `.gitignore`, `.gitattributes`, `CLAUDE.md`, 루트 `README.md`, `docs/task-logs/`(규칙, 템플릿)를 만들었다.
4. 첫 커밋을 `origin/main`에 push했다.
5. Vercel CLI로 로그인(브라우저 승인) → 프로젝트 `ping9` 생성 → 폴더 연결 → 운영 배포.
6. `vercel git connect`로 GitHub 저장소 연결을 시도했으나 실패했다.

### 주요 결정

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| 기본 브랜치 `main` | 계획 문서(T1.1.3)가 main 브랜치 보호를 전제로 함 | `master` |
| 줄 끝을 LF로 통일 (`.gitattributes`) | 첫 `git add`에서 파일마다 CRLF 변환 경고가 나옴. OS가 섞이면 의미 없는 diff가 생김 | 각자 `core.autocrlf` 설정에 맡김 |
| `_bmad/config.user.toml`, `.claude/settings.local.json`은 커밋하지 않음 | 파일 머리말이 개인별 설정이라고 밝히고 있음 | 전부 커밋 |
| `docs/project-plan/project-plan.zip`은 커밋하지 않음 | 같은 폴더의 문서를 묶은 사본. 파일은 지우지 않고 로컬에 둠 | 커밋 |
| Vercel 프로젝트 하나, 루트 디렉터리는 저장소 루트, 설정은 `vercel.json` | 화면과 `/api`가 같은 출처여야 함 (AD-12, 쿠키 기반 인증). 설정이 코드로 남아 PR로 검토됨 | web과 api를 Vercel 프로젝트 둘로 분리 |
| 자리표시 화면 `apps/web/index.html` + `outputDirectory: "apps/web"` | 빌드할 앱이 아직 없음. 출력 폴더를 지정하지 않으면 저장소 루트가 그대로 공개되어 계획 문서가 노출됨 | 앱이 생길 때까지 배포 연결을 미룸 |
| DB 후보는 Neon (Vercel Marketplace, 무료 플랜 `free_v3`) | 설계가 PostgreSQL + Drizzle. Vercel 문서에 따르면 Vercel Postgres는 없어졌고 Neon으로 옮겨짐 | Supabase (인증·스토리지까지 딸려 옴), Upstash Redis (관계형이 아님) |
| DB 리전은 `sin1` (싱가포르) | CLI가 주는 선택지(cle1, iad1, pdx1, fra1, lhr1, syd1, sin1, gru1) 중 한국에서 가장 가까움. 🟡 Functions 리전도 T2.1.1에서 `sin1`로 맞춰야 DB 왕복이 짧아짐 | `iad1` (Vercel Functions의 기본 리전과 같지만 사용자에게서 멂) |
| Neon Auth는 끔 (`auth=false`) | 인증은 설계대로 better-auth를 씀. 기본값은 켜짐 | 켜 둠 |
| DB는 운영(production) 환경에만 연결 | 미리보기 배포와 로컬 개발이 운영 데이터를 건드리지 않게 함. 미리보기·개발용 DB는 T2.1.2에서 정함 | 세 환경 모두에 같은 DB 연결 (CLI 기본값) |

### Neon 무료 플랜 한도와 계획 수치

한도는 2026-11-05에 Neon 공식 문서(neon.com의 plans, pricing, free-plan-limits FAQ, history-window, backup-restore)에서 확인했습니다. 계획 수치는 [02 문서 NFR-5, NFR-6](../project-plan/02-requirements.md)과 [05 문서 5.5절](../project-plan/05-security-and-testing.md#55-자원-제한)의 것입니다.

| 한도 | 값 | 넘으면 | 계획과 견주면 | 필요한 조치 |
|---|---|---|---|---|
| 저장 용량 | 프로젝트당 1GB | 용량을 늘리는 쓰기가 실패 | 계획의 최악 경우가 계정 200개 × 계정당 5MB = **1,000MB로 한도와 같음.** 인덱스와 인증 테이블을 더하면 넘음. 실제 수업 규모(30명)에서는 수십 MB로 예상 🟡 | 전체 계정 수 상한을 100개로 낮추거나 계정당 용량을 줄임 (05 문서 5.5절의 미결 항목). T2.3.2 |
| 변경 이력 | 6시간, 1GB까지 | 문서에 없음 | 자동 저장이 3초 대기 뒤 문서 전체를 다시 씀. 수업 중에 이력이 빠르게 쌓일 수 있음. ⚠️ 이력이 저장 용량 1GB에 포함되는지는 문서에 없음 | 30명 부하 테스트(T2.8.2) 뒤 Neon 콘솔에서 사용량 확인. 문제가 되면 이력 기간을 줄임 |
| 연산 시간 | 프로젝트당 월 100 CU-hours | **다음 달까지 DB가 멈춤** | 수업 시간에만 쓰면 여유. 🟡 가장 작은 크기(0.25 CU)로 한 달 내내 깨어 있으면 약 180 CU-hours로 한도를 넘음 | DB를 주기적으로 깨우는 것을 만들지 않음. `/api/health`는 DB 연결을 포함하므로(03 문서 3.5절) 외부 감시나 예약 작업으로 주기 호출하지 않음. T2.2.3 |
| 자동 확장 | 2 CU까지 | — | 2 CU로 올라가면 연산 시간을 8배 빨리 씀. ⚠️ 무료 플랜에서 상한을 낮출 수 있는지는 문서에 없음 | Neon 콘솔에서 상한 설정이 되는지 확인. T2.1.2 |
