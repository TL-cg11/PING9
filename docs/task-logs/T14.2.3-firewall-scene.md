## 1. 목표와 완료 기준

시뮬레이션에서 펭귄이 Firewall을 지날 때 규칙이 허용했는지, 막았는지(DROP·REJECT)를 그림으로 보인다.

- [x] Firewall 그림을 눈 덮인 분홍 벽돌 벽과 방패로 바꿈 (T14.2.1의 불꽃 벽 대신)
- [x] 허용: 펭귄이 다가가면 방패가 초록 체크로 바뀌고 "허용" 말풍선. 펭귄은 멈추지 않고 지나가고, 지나간 뒤 방패는 분홍으로 돌아감
- [x] DROP: 방패가 빨간 X, "규칙 N 차단". 물고기가 방패 쪽으로 빨려 들어가고 펭귄은 눈가루처럼 흩어짐 (콘솔은 `Request timed out.`)
- [x] REJECT: 방패가 빨개지고 펭귄이 멈칫(`!`)한 뒤 물고기를 든 채 돌아서 왔던 길로 걸어감 (콘솔은 `Destination net unreachable.`)
- [x] 규칙 없이 체인의 기본 정책으로 막히면 "기본 정책 차단"
- [x] 공통 완료 조건: lint, 타입 검사, 단위 테스트, 빌드 통과. 리뷰는 PR에서

## 2. 진행 방식

1. 디자인 사본(5180)에서 지금 앱의 펭귄·물고기 그림으로 세 장면 시안을 만들어 골랐다. Firewall 그림은 팀의 "방화벽·눈 수정" 시안 이미지를 32×32 SVG로 다시 그렸다 (원본은 바탕이 불투명한 PNG라 그대로 못 씀).
2. 엔진의 추적을 실제로 찍어 세 경우의 이벤트를 확인했다. 엔진(SDY 담당)은 고치지 않고 추적만 읽는다.
   - 허용: Firewall이 같은 `frameId`를 `forward`한다. 허용 규칙의 번호는 추적에 없다.
   - DROP: `drop` `FIREWALL_BLOCKED` {target "DROP", rule}. 그 뒤로 아무것도 없다.
   - REJECT: 같은 `drop` 다음에, 그 drop을 부모로 하는 ICMP destination-unreachable `reply`가 돌아간다.
3. 5180에 구현해 headless Chrome으로 세 경우를 재생해 캡처로 확인했다. 장비 목록의 Firewall 크기와 가로 자리를 사용자 확인을 받아 조정했다.
4. 저장소로 5180의 이번 변경만 diff로 옮겼다. T6.3.1 카드 PR에 함께 넣었다 (사용자 결정).

### 주요 결정

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| 차단에만 규칙 번호, 허용은 "허용"만 | 엔진이 허용한 규칙의 번호를 추적에 남기지 않는다. 엔진을 고치지 않는다 | 엔진에 허용 규칙 번호 추가 |
| 방패는 펭귄 층이 장비 그림 위 같은 자리에 겹쳐 그림 | 장비 아이콘은 재생 상태를 모른다. 펭귄 층만 시각을 안다 | 장비 아이콘에 상태 넘기기 |
| DROP 장면은 놓침 그림(drop)을 펭귄 부분과 물고기 부분으로 잘라 따로 움직임 | 새 그림 없이 지금 펭귄·물고기 그림을 쓴다. 경계는 그림의 픽셀에 맞췄다 (×와 짧은 선은 빼고) | 새 그림 파일 |
| DROP은 Firewall 바로 앞에서 흩어짐 | 실제로는 Firewall 안에서 버려지지만, 다른 놓침과 같이 버려진 장비 앞에 그린다 | Firewall 안에서 사라짐 |
| REJECT로 돌아오는 펭귄은 빨간 물고기(ICMP 오류)를 좌우 뒤집어 그림 | 엔진이 보내는 것이 ICMP 오류다. 돌아서 걷는 것이 보인다 | 파란 물고기를 든 채 돌아감 |
