## 2. 진행 방식

`forwarding.test.ts`를 먼저 쓰고(모듈이 없어 실패) `forwarding.ts`를 만들었다.

`switchForward`는 순수 함수다. 구성, 포트가 켜져 있는지 알려 주는 함수, MAC 주소 테이블, 가상 시각, 받은 포트, 프레임을 받아 새 테이블과 내보낼 포트 목록을 돌려준다. 받은 값은 고치지 않는다 (AD-5).

### 주요 결정

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| kernel보다 먼저, 순수 함수로 | kernel이 아직 없다. 손으로 만든 프레임으로 규칙 전부를 테스트할 수 있다 | kernel을 기다림 |
| 테이블은 `(vlan, mac)`마다 한 줄인 배열, VLAN·MAC 순 | 같은 내용이면 항상 같은 값이라 비교와 스냅샷이 쉽다. 포트가 8개라 크기가 작다 | `Map` (순서가 넣은 순서에 달림) |
| 이 Task에서는 모든 프레임이 VLAN 1 | VLAN을 나누는 규칙은 T5.2.1(access)과 T5.3.1(trunk)에서 `classify`와 `egress` 두 자리에 넣는다 | 한 번에 다 넣음 |
| 배운 포트가 꺼져 있으면 그 항목을 쓰지 않고 flooding | 정리 함수가 불리기 전에도 꺼진 포트로 보내지 않는다 | 꺼진 포트로 보내고 폐기 |
| 같은 포트에서 다시 본 주소는 `learned`로 알리지 않음 | `learned`는 "MAC을 배웠다" 이벤트의 재료다. 시각만 고친 것은 이벤트가 아니다 | 매번 알림 |
| 만료된 항목은 프레임을 처리할 때 테이블에서 지움 | 설계는 "조회할 때 없는 것으로 친다"다. 지우면 테이블이 커지지 않는다 | 남겨 두고 조회 때만 거름 |

## 6. 계획과 달라진 점

- **전달 규칙이 kernel(T1.7.2)보다 먼저 나왔다.** 계획은 T1.7.3이 T1.7.2에 기댄다 (설계 12절).
- **Task를 둘로 나눴다.** kernel 없이 되는 부분이 이 문서이고, kernel 연결은 T5.2.2의 기록에 적는다 (설계 9절).
- **화면의 MAC 주소 테이블은 여전히 비어 있다.** 프레임이 실제로 흐르지 않아서다.

### 검토에서 나온 것 (2026-11-06)

- **`pruneMacTable`이 모드가 바뀐 포트의 항목을 남겼다.** 설계 6.3절은 모드가 바뀐 포트의 항목을 지우라고 한다. 지금 구성만으로는 무엇이 바뀌었는지 알 수 없어서, 바뀌기 전의 구성(`previousConfig`)을 받으면 모드나 access VLAN이 바뀐 포트의 항목을 지우게 했다.
- **MAC 주소의 대소문자**: `FF:FF:FF:FF:FF:FF`를 브로드캐스트로 보지 않았다. 프레임의 주소를 소문자로 바꿔 다루게 했다. engine이 만드는 주소는 원래 소문자다.

## 7. 남은 일과 다음 Task에 전할 것

- **kernel 담당에게**: Switch 모델은 `switchForward`의 결과를 이렇게 옮기면 된다. `ingressDrop` → 폐기 이벤트, `learned` → `MAC_LEARNED`, `outputs` → 포트마다 프레임 보내기(`flooded`면 `FRAME_FLOODED`, 아니면 `FRAME_FORWARDED`), `samePort` → 내보내지 않음. `isPortUp`에는 `computeViews`의 포트 상태가 `up`인지를 넘긴다. 구성이나 링크가 바뀌면 `pruneMacTable`을 부른다. `view()`는 `macTableView`를 돌려준다.
- `samePort`를 Trace에 어떤 코드로 적을지는 정하지 않았다 (`NOT_FOR_ME`는 뜻이 다르다).
- T5.2.1이 `classify`와 `egress`에 access VLAN을, T5.3.1이 trunk를 넣는다.
