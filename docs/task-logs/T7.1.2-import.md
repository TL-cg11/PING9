## 2. 진행 방식

1. 설계안(T7.1)의 결정을 따랐다. 사용자가 "시안대로" 정했다 (2026-11-11). T7.1.1과 같은 커밋으로 올린다 (사용자 결정).
2. `shared`: `parseDocumentJson`의 절차를 앞(크기 → JSON → 금지 키·깊이)과 뒤(`schemaVersion` → 변환 → 검증)로 나눠, 그 사이에 겉 포장 확인을 끼운 `parseExportJson`을 만들었다. `parseDocumentJson`의 동작은 그대로다 (기존 테스트 통과).
3. web: 파일 읽기(`readImportFile`)와 확인 여부(`needsReplaceConfirm`)는 순수 함수로 두고 단위 테스트. 고르기·확인 창·알림은 `app.tsx`.
4. 바꾸면 화면 상태를 처음으로 되돌린다: `simulator.load`가 Runtime을 비우듯, 터미널과 그 기록, 선택, 펭귄, 도구를 비운다.
5. 개발 서버를 띄워 브라우저를 자동으로 조작해 8단계를 확인했다 (4절).

### 주요 결정

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| 가져오면 **지금 캔버스를 바꾼다**. 장비가 있으면 확인 창 | 목록 화면과 서버가 없어 "새 토폴로지"를 둘 곳이 없다 (설계 결정 5) | 계획대로 새 토폴로지 (불가) |
| 빈 캔버스면 묻지 않는다 | 잃을 것이 없다 | 항상 물음 |
| 확인 창은 화면 안의 창(`ConfirmDialog`). 확인 버튼에 포커스, Esc와 바깥 누르기는 취소 | 모양이 맞고 테스트할 수 있다 (설계 결정 6) | 브라우저 `confirm()` |
| 겉 포장 없는 Document 파일은 거부, 새 오류 `IMPORT_NOT_EXPORT_FILE` "PING9에서 내보낸 파일이 아니에요" | 계획의 형식 하나로 (설계 결정 4). 형태 오류보다 무엇이 틀렸는지 분명하다 | Document만 있어도 받음 |
| 안쪽 문서의 형태 오류 위치는 파일 기준(`document.devices.0...`) | 파일을 열어 찾을 때 맞는 위치다 | 문서 기준 위치 |
| 겉 포장의 다른 키는 무시 | 문서 스키마도 모르는 키를 버린다. 나중에 겉 포장에 정보를 더해도 옛 버전이 읽는다 | 거부 |
| 이름은 `checkTopologyName`(1~100자, 제어 문자 없음)으로 검증 | 서버가 생기면 같은 규칙으로 저장한다 (SEC-7) | 검증 없음 |
| 실패는 캔버스 위 가운데의 알림, 닫을 때까지 보인다 | FR-45 "가져오기 오류는 구별되는 문구", 놓치지 않게 | 몇 초 뒤 사라짐 |
| 바꿀 때 진행 중인 ping을 멈추고 터미널 기록을 버린다. 모드는 그대로 | 다른 토폴로지의 콘솔 기록이 남으면 헷갈린다. 모드는 화면의 설정이다 | 터미널을 남김 |
| 확인 창이 열린 동안 Delete로 장비를 지우지 않는다 | 확인 버튼에 포커스가 있어 Delete가 캔버스에 닿았다 | 그대로 |
| 고르기 창은 `.json,application/json` | 내보낸 파일은 `.ping9.json`이다 (설계 결정 3) | 모든 파일 |

## 6. 계획과 달라진 점

- **가져오면 새 토폴로지가 아니라 지금 캔버스를 바꾼다** (확인 창). 계획은 목록 화면의 가져오기 → `POST /api/topologies`. 선행 T2.3.2(생성 API)와 T2.3.3(목록 화면)이 없다. 서버가 생기면 계획대로 바꾼다.
- 가져오기 버튼이 목록 화면이 아니라 편집기 상단 막대에 있다.
- 새 오류 코드 `IMPORT_NOT_EXPORT_FILE`를 더했다.
- E2E 대신 단위 테스트의 왕복과 브라우저 자동 조작으로 확인했다.
