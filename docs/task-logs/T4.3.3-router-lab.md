## 2. 진행 방식

공유 라우터 예시는 T4.2.1에서 준비했다. 최종 검사에서는 예시의 IP·포트 설정을 비운 뒤 PC 패널이 쓰는 pc/set-ip와 Router 공개 콘솔 명령만으로 구성했다. 설정 조회뿐 아니라 실제 echo 응답·Trace 성공을 판정한다.

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| 스위치 없는 구성으로 검증 | 사용자가 승인한 직접 연결 구성, 미구현 Switch 모델과 독립 | Switch를 통과한 것처럼 처리 |
| 새 Chrome 탭에서 수동 검사 | 기존 사용자 실습 탭의 배치를 보존 | 기존 탭 재설정 |

## 4. 결과와 검증

Node 24.19.0에서 최종 실행:

```text
pnpm check
lint / typecheck / build 통과
scripts 35 + shared 311 + engine 1379 + web 304 + api 2 = 2031 tests passed
pnpm check:secrets
추적 파일 590개 통과
```

자동 검사 범위:

- 한 Router의 양방향 ping과 응답 TTL 127, 두 Router의 양방향 정적 경로와 응답 TTL 126.
- Linux 응답 TTL 62, 게이트웨이 ping, Router 자체 ping·출발 IP 선택·show arp.
- IP 유지·MAC 변경·TTL 감소·동일 frameId 유지, ARP 재사용과 미응답 재시도 종료.
- shutdown·케이블 제거·장비 삭제·게이트웨이 누락·가는/귀환 경로 누락, 복구와 load 초기화.
- 순환 경로의 TTL=0 폐기, 실제 ICMP 시간 초과 수신, ICMP 오류 자체의 순환 억제.
- 기본 경로와 더 구체적인 /32 선택의 실제 전송 결과, Trace 계약 검증.

실제 Chrome에서는 별도 `http://127.0.0.1:5174/` 탭에 PC5—R1—PC6을 새로 배치했다. PC 패널에서 192.168.1.10/24, 192.168.2.10/24와 게이트웨이를 적용하고 케이블로 연결했다. R1 CLI로 양쪽 IP와 no shutdown을 설정한 뒤 PC5에서 ping했다.

```text
Reply from 192.168.2.10: bytes=32 time=8ms TTL=127
Reply from 192.168.2.10: bytes=32 time=4ms TTL=127
Reply from 192.168.2.10: bytes=32 time=4ms TTL=127
Reply from 192.168.2.10: bytes=32 time=4ms TTL=127
Packets: Sent = 4, Received = 4, Lost = 0 (0% loss)
```

## 5. 추정과 실제

추정 0.5인일, 실제 인일은 별도 측정하지 않았다. 실습 설명과 실패 시나리오 안내를 함께 작성했다.

## 6. 계획과 달라진 점

계획의 PC 2·Router 2·Switch 2 대신, 승인된 PC 2·Router 2 구성을 검증했다. Switch 모델 구현 후 원래 예시를 추가해야 한다. 상단 ping 버튼과 상세 Trace 뷰어는 이번 범위가 아니며 장비 콘솔로 실행한다. Windows의 Received는 오류 수신도 포함하므로 성공 판정은 bytes=32 응답과 Trace.status로 한다.
