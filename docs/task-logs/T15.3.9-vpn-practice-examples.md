## 2. 진행 방식

기존 SSL 코드와 자료를 보존하고 새 문서 브랜치를 만들었다. 같은 장비 배치·물리 주소를 쓰되 R1/R3를 site-to-site VPN 양끝으로, R2를 일반 중간 Router로 구성했다. 기존 ?lab=gre/ipsec 예제와 과거 계획/기록은 보존하고 새 가져오기 파일을 제공한다.

R1/R3에는 반대 WAN 경로만, R2에는 직접 연결 WAN 경로만 준다. VPN 설정 전에는 PC 간 ping이 실패한다. GRE는 가상 터널 IP를 next-hop으로, IPsec은 R2의 물리 IP를 next-hop으로 상대 LAN 경로를 추가한다. 양쪽 설정을 문서에서 그대로 입력한 결과를 완성 파일로 저장했다.

## 4. 결과와 검증

실습 검증용 임시 Vitest에서 문서 코드 블록을 추출해 실행했다.

```text
pnpm --filter @ping9/engine exec vitest run src/vpn/vpn-practice-rehearsal.test.ts
  Test Files 1 passed (1)
  Tests 3 passed (3)
  Duration 473ms
```

1. 빈 Simulator에 PC 2대·Router 3대·케이블 4개를 만들고 공통 물리망 명령을 실행했다. 각 PC의 게이트웨이, R1↔R3 WAN ping은 성공하고 PC 간 ping은 실패했다.
2. GRE 문서의 양쪽 설정과 중단/복구를 실행했다. 양방향 PC 응답 TTL 126, GRE 생성·R2 중계, Trace 검증 통과, 완성 JSON을 새 Simulator에 가져온 뒤 양방향 ping 성공을 확인했다.
3. IPsec도 같은 순서로 양방향 TTL 126·ESP 생성/R2 중계·active SA·정책 중단과 복구·JSON 재가져오기를 확인했다.

IPsec에서 한쪽 PSK 변경 후 원복만 하면 상대의 anti-replay 상태와 어긋날 수 있음을 재현했다. 실제 IKE 재협상은 없는 기존 동작이므로 제품 코드를 바꾸지 않고, 최종 실패/복구는 sequence를 보존하는 정책 disable/enable로 안내한다. PSK 변경 뒤 anti-replay가 나올 때 양쪽 실행 상태를 완성 파일 재가져오기로 초기화하는 설명도 넣었다.

검증 후 임시 테스트 파일은 삭제했다. 제품 코드 변경이 없어 전체 빌드/테스트는 반복하지 않았다. 수동 브라우저 조작은 하지 않았다. 문서·JSON의 상대 링크/비밀값/공백 검사를 별도 수행했다.
