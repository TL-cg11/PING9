## 2. 진행 방식

1. 병합된 kernel(T1.7.1, PR #27)의 `SimContext`와 기대 결과 `twoPcPingTrace`(shared 예시)를 기준으로 모듈 모양을 정했다.
2. ARP는 장비 종류를 모르는 프로토콜 모듈(`ArpModule`)로 만들었다. 장비 모델이 객체를 들고 있고, `ctx`는 콜백마다 받는다. 테이블은 ping 회차가 바뀌어도 남는다.
3. 링크 전달(T1.7.2)이 아직 없어 프레임 내보내기는 `ArpHost.transmit`으로 받았다. 테스트는 **진짜 kernel**에 가짜 `transmit`(1000 µs 뒤 상대에게 건넴)을 붙여 돌렸다.

### 주요 결정

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| 보관 패킷은 프레임이 아니라 "만드는 법"(`PendingSend.build`)으로 두고, MAC을 안 뒤에 `createFrame` | 예시에서 ICMP의 frameId가 3이다. 미리 만들면 1이 된다 | 보관한 프레임을 `updateFrame`으로 바꾸기 |
| 부모 관계를 직접 넘김: `LEARNED`·`REPLY_SENT`의 부모는 `RECEIVED`, 보관 패킷의 첫 이벤트의 부모는 `LEARNED` | kernel의 기본 `parentSeq`(콜백의 원인)를 쓰면 예시와 달라진다 | 기본값 |
| 요청을 받으면 보낸 쪽을 기록한다 | 예시 seq 2가 정했다 | — |
| 받은 ARP는 RFC 826대로: 이미 아는 IP면 고치고, 대상 IP가 자기일 때만 새로 넣는다 | 표준이다. 시뮬레이터의 응답은 요청에 대한 것뿐이라 보통 결과는 같다 | 모든 응답 기록, Linux식(없던 IP의 응답은 버림) |
| 무응답이면 0초와 1초에 요청, 2초에 `ARP_TIMEOUT` 폐기 하나 | 다시 묻는 동작을 Trace에서 볼 수 있고, 계획의 "2초 뒤 폐기"(02 문서 A5)가 그대로다 | 요청 1번 (단순), 3번 (Linux와 같지만 3초) |
| 무응답 폐기는 대기열마다 하나, 마지막 요청 프레임으로 기록 | `record`에는 `Frame`이 필요한데 보관 패킷은 아직 프레임이 아니다. ping은 회차마다 패킷 하나라 결과는 같다 | 보관 패킷마다 하나 |
| 항목 만료 없음. `clear`(`arp -d`)로 비운다 | FR-29에 없다. 가상 시계는 통신이 돌 때만 가서 실제 만료 시간(15~45초)이 지나는 일이 거의 없다. 실제 시계는 결정성을 깬다 (AD-5) | 실제 시계로 만료 |
| 응답을 받으면 `cancelTimer` | kernel에 취소가 있다. 취소한 타이머는 시계도 그 시각으로 보내지 않는다 | 회차 번호로 옛 타이머 거르기 |
| 보냄 이벤트는 ARP가 기록하고 `transmit`은 보내기만 | 실제 OS도 ARP가 프레임을 만들고 드라이버는 내보내기만 한다. 링크 없음 폐기는 T1.7.2가 기록한다 | `transmit`이 기록 |
| `onPortChanged(port)`: 포트의 IP가 바뀌거나 링크가 지워지면 그 포트의 항목을 지운다 | 실제도 링크가 끊기면 그 인터페이스 항목을 지운다. 부르는 쪽은 장비 모델 | 그대로 두기 |
| `discardPending()` | 회차가 LOOP_GUARD로 중간에 멈추면 타이머가 사라져 대기열이 남는다. 그 프레임은 다음 Trace에서 쓸 수 없다 | 남겨 두기 (다음 회차에 요청이 나가지 않음) |

테스트가 확인하는 것: 예시 `twoPcPingTrace`의 seq 0~6과 같음(seq 6은 테스트의 가짜 ICMP), 이미 알면 바로 보냄, 회차가 바뀌어도 테이블이 남음, 무응답(요청 2번, 2초에 폐기, 부모 관계, `primaryDropSeq`), 링크 없음, 자기 것이 아닌 요청(`NOT_FOR_ME`, 실패 원인 아님), RFC 826 갱신, 여러 패킷 대기, 타이머 취소, 다른 모듈의 타이머, 대상이 자기가 아닌 응답, `clear`·`onPortChanged`, IP 숫자 순 정렬, `discardPending`, 결정성, `validateTrace` 통과.

화면에서는 확인하지 않았다. 장비 모델(T1.7.2·T1.8.3)이 없어 아직 ping이 돌지 않는다.

## 6. 계획과 달라진 점

- **선행 T1.7.2 없이 했다.** 프레임 내보내기를 `ArpHost.transmit`으로 받아 두었다. T1.7.2가 들어오면 장비 모델이 이것을 채운다.
- **무응답 때 요청을 두 번 보낸다** (계획은 "2초 대기 뒤 폐기"만 적었다). 폐기 시각 2초는 같다.
- **담당:** 분담안에서는 Router 담당 일이었는데 yysong1249가 했다.

## 7. 남은 일과 다음 Task에 전할 것

- **T1.7.2(링크 전달, 장비 모델):** `ArpHost`를 채운다. `transmit`은 링크 상대 포트로 `ctx.sendFrame(…, LINK_DELAY_MICROSECONDS)`를 부르고, 링크가 없거나 포트가 꺼졌으면 폐기를 기록한다. 받은 프레임에 `arp`가 있으면 `onArp`, 타이머는 `onTimer`(false면 다른 모듈의 것). 회차를 시작할 때 `discardPending()`, 포트의 IP가 바뀌거나 링크가 지워지면 `onPortChanged(port)`.
- **T1.8.2(IPv4·ICMP):** 다음 홉 IP를 골라 `send(ctx, port, nextHopIp, pending)`을 부른다. `pending.onSend`가 `ICMP_ECHO_REQUEST_SENT` 같은 보냄 이벤트를 기록하고(`outPort`, `linkId`, 받은 `parentSeq`), ARP가 그 뒤에 `transmit`을 부른다.
- **T1.8.3(PC 모델, `arp -a`·`arp -d`):** `view()`, `clear(ip?)`.
- 테스트의 가짜 세상은 3대일 때 다 배운 Switch처럼 동작한다(브로드캐스트는 모두에게, 나머지는 그 MAC에게만). 진짜 Switch 연결은 T1.7.3의 kernel 연결 때 본다.
