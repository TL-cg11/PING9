## 2. 진행 방식

1. 테스트를 먼저 썼다 (`terminal-state.test.ts`에 7개, `keys.test.ts`). 함수가 없어 실패하는 것을 확인했다.
2. `terminal-state.ts`에 `completed`와 `showHelp`, `keys.ts`에 `keyAction`을 만들고 터미널 창과 `app.tsx`에 연결했다.
3. 브라우저에서 확인하다가, 키 입력 없이 들어온 `?`(붙여 넣기 등)가 입력란에 그대로 남는 것을 봤다. 실패하는 테스트 8개를 먼저 쓰고 `helpRequest`로 처리했다.

화면은 완성과 도움말을 계산하지 않는다. `ConsolePort.complete`와 `help`를 부르고 결과를 그릴 뿐이다 (AD-8).

### 화면에서의 동작

| 입력 | 동작 |
|---|---|
| Tab | 마지막 단어가 명령어 하나로 정해지면 그 단어와 빈칸으로 바뀐다. 아니면 아무 일도 없다 |
| `?` | 화면 기록에 `프롬프트 입력중인줄?` 한 줄과, 올 수 있는 단어·설명이 열을 맞춰 나온다. 입력란의 글은 그대로다 |
| `?` (올 수 있는 단어가 없을 때) | "여기에 올 수 있는 명령어가 없어요" 한 줄 |
| Shift+Tab | 가로채지 않는다 (이전 요소로 포커스 이동) |

### 주요 결정

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| 키 판단을 순수 함수(`keyAction`)로 뺌 | 화면 테스트는 DOM 없이 돈다. 어떤 키를 가로채는지를 함수로 두면 테스트할 수 있다 | 컴포넌트 안에서 판단: 테스트할 길이 없음 |
| `?`를 입력란의 `onChange`에서도 잡음 (`helpRequest`) | 붙여 넣기와 화면 자판은 `keydown` 없이 글을 넣는다. `?`는 어떤 명령어에도 들어가지 않는 글자다 | `keydown`만 처리: 붙여 넣은 `show ?`가 "알 수 없는 명령어"가 됨 |
| 도움말을 본 줄은 이전 명령어(이력)에 넣지 않음 | 실행한 줄이 아니다. 위 화살표로 `sh?`가 나오면 방해가 된다 | 이력에 넣음 |
| `?`는 실행과 같은 대기열로 | 앞 명령의 결과가 화면에 쓰이는 도중에 도움말 줄이 끼어들거나 덮이지 않는다. 앞 명령이 모드를 바꿨으면 바뀐 모드의 도움말이 나온다 | 바로 화면 기록에 씀 |
| Tab만 가로채고 Shift+Tab은 그대로 | 입력란에서 Tab을 가로채면 키보드만 쓰는 사람이 터미널에서 나갈 길이 없다 | 둘 다 가로챔 |
| 한글을 조합하는 중에는 Enter, Tab, `?`를 가로채지 않음 | 조합을 끝내는 키 입력이 명령으로 읽히면 글자가 두 번 들어가거나 덜 끝난 줄이 실행된다 | — |

## 6. 계획과 달라진 점

- **선행 Task가 T1.6.2(콘솔 창)가 아니라 T5.4.1의 터미널 창이다.** T5.4.1에서 만든 창에 연결했다.
- **`xterm`의 줄 편집기가 아니라 입력란(`<input>`)이다** (T5.4.1의 결정). 그래서 "줄 편집기 단위 테스트"는 키 판단과 상태 함수의 테스트로 했다.

## 7. 남은 일과 다음 Task에 전할 것

- **PC·Router 터미널도 같은 창을 쓴다.** 자기 명령 정의를 `console.ts`에 넣으면 Tab과 `?`가 바로 동작한다.
- **도움말의 설명은 영어다** (engine이 만든 글 그대로). 한국어로 바꾸는 방법은 T3.2.2 기록 문서 7절.
- **캔버스의 안내 문구에는 Tab과 `?`가 없다.** 시안의 문구를 그대로 두었다.
- T3.5.2에서 오류 줄 아래에 틀린 위치를 가리키는 `^` 줄을 넣는다. engine은 이미 `position`을 돌려준다.
