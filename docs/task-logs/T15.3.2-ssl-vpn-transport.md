## 1. 목표와 완료 기준

- [x] IPv4 protocol 6과 교육용 TCP header를 표현하고 경계 검증.
- [x] PC→Router→Firewall→PC를 실제 ARP·케이블·커널로 전달.
- [x] TCP 목적지·출발 포트의 양방향 iptables 규칙 적용.
- [x] TTL·ARP·링크 장애·차단 규칙 trace와 기존 동작 회귀 확인.
- [x] TCP를 ICMP로 오인하지 않는 재생·이벤트 상세.
- [x] 로컬 전체 검사와 빌드.
- [ ] 팀 리뷰. 세션·인증·가상 IP·VPN 연결은 다음 구현 범위.

## 2. 진행 방식

기존 코드는 TCP 규칙을 저장할 수 있었으나 TCP 프레임이 없어 규칙에 일치하는 실제 세그먼트를 전달할 수 없었다. SSL VPN 연결 상태를 우선 성공으로 바꾸는 대신, 계획의 선행 작업인 바깥 전송부터 구현했다. 커널은 재사용했다.

새 PC의 `TcpSegmentHost`는 ARP와 물리 인터페이스 설정을 재사용하고 `PendingSend`로 케이블에 보낸다. 송신 전 기본 값 범위를 확인하며 받은 세그먼트 목록은 실행마다 비우고 최대 256개만 유지한다. Router/Firewall은 전달 시 TCP 헤더를 누락하지 않는다. TCP 이벤트·포트 표시와 재생 kind를 별도로 추가했다.


9개 전송 시나리오는 실제 모델과 커널을 사용한다. 2홉 TTL 감소·TCP 필드/payload 보존·ARP·양방향 필터·먼저 맞는 규칙·두 장비 각각 TTL 만료·물리 장애·ARP timeout·잘못된 Trace·기존 프로토콜 구분을 포함한다. 웹 테스트는 TCP 세그먼트가 ping으로 그려지지 않고 이벤트 상세에 포트와 방화벽 실패 사유가 표시되는지 확인한다.

자동 테스트에서 생성한 세그먼트만 실행했다. 실제 브라우저 VPN 접속 검증은 하지 않았고, 현재 공개 CLI에 TCP 테스트/SSL VPN 접속 명령을 추가하지 않았다.

## 5. 추정과 실제

전체 SSL VPN 계획은 여러 단계다. 이번 결과는 전송 선행 부분이며 전체를 완료한 것으로 계산하지 않는다.

## 6. 계획과 달라진 점

기존 main의 계획 문서는 수정하지 않았다. T15.3.1의 SSL VPN 서버·PC 설정 계약은 후속으로 남기고, TCP 프레임/전달 계약과 Firewall 실험을 먼저 구현했다. 실제 TCP stack/TLS/암호화/OpenVPN 호환은 없다.
