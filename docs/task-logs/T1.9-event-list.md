## 2. 진행 방식

1. 5180에서 시안을 고쳐 가며 사용자가 정했다 (2026-11-12). 자리는 하단 도크가 아니라 오른쪽 패널의 "상세 정보 / 이벤트" 탭으로 정했다.
2. 로그가 쌓이는 방식을 두 가지 놓고 사용자가 A를 골랐다. A: 펭귄 재생에 맞춰 줄이 하나씩 나타난다. B: ping이 끝나면 한꺼번에.
   - engine은 ping 한 회차를 가상 시간으로 한 번에 계산해 Trace 하나로 남긴다. 그래서 줄마다 "재생 시작부터 몇 ms에 보일지"를 재생 시간표에서 계산했다 (`replay/reveal.ts`).
3. 시간은 시뮬레이션 시계(T0.15)를 따른다. 멈추면 목록도 서고, 속도를 바꾸면 같이 바뀐다.
4. 문구는 engine이 남긴 `{ code, params }`로 화면에서 만든다 (AD-14). 조사는 기존 `particles.ts`를 쓴다.
5. 5180에서 브라우저로 확인한 뒤 저장소로 옮기고 테스트를 썼다. `twoSwitchVlanDocument` 예시를 쓴다: PC1 → PC3는 SW2의 trunk에서 막히고(VLAN 10 불허), PC2 → PC4는 된다.
6. T0.18(패널 폭 조절, 빈 카드 그림)과 빈 카드의 같은 줄을 고쳐서 그 브랜치 위에 올렸다.

### 주요 결정

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| 오른쪽 패널의 탭 (상세 정보 / 이벤트) | 하단 도크를 두면 캔버스가 줄어든다. 패널 폭은 T0.18로 넓힐 수 있다 | 계획대로 하단 도크 |
| 시뮬레이션 모드에서만 탭이 보인다 | 실시간은 콘솔만으로 결과를 보는 모드다 (T0.13). 재생 동기화도 시뮬레이션에만 있다 | 두 모드 모두 |
| 줄이 재생에 맞춰 나타난다 (A) | 펭귄이 지나간 곳까지만 보여야 화면과 기록이 맞는다는 사용자 결정 | 끝나면 한꺼번에 (B) |
| 탭은 사용자가 누를 때만 바뀐다. 새 기록이 생기면 이벤트 탭에 빨간 점 | 설정 중에 탭이 저절로 바뀌면 방해된다 | ping마다 이벤트 탭으로 이동 |
| 이벤트 탭은 마지막으로 재생을 시작한 ping을 따라간다. 사용자가 다른 추적을 고르면 그것을 보이다가 새 ping이 시작되면 다시 따라간다 | 방금 실행한 결과를 바로 본다 | 항상 고른 추적만 |
| 실패 사유는 재생이 끝난 뒤에 보인다. 원인 줄은 나타나는 순간부터 빨갛다 | 펭귄이 넘어지기 전에 결과를 알려 주지 않는다 | 처음부터 사유 표시 |
| 선택한 이벤트는 `app.tsx`의 상태로 | 이벤트 탭과 캔버스만 쓴다. 따로 store를 둘 만큼 쓰는 곳이 없다 | 별도 web store |

## 6. 계획과 달라진 점

- 네 Task를 한 PR, 한 기록 문서로 묶었다. 같은 화면이라 따로 나누면 중간 상태가 화면에서 쓸모없다.
- 이벤트 목록 자리: 계획은 "하단 도크의 이벤트 목록 탭"인데 오른쪽 패널의 탭으로 했다. 시뮬레이션 모드에서만 보인다.
- T1.9.3 "선택한 이벤트를 web store에 보관": 별도 store 대신 `app.tsx`의 상태로 했다.
- 줄이 펭귄 재생에 맞춰 나타난다. 계획에서는 T6.2.2(이벤트 목록 동기화)에 가까운 내용인데 그중 "재생 위치에 맞춰 목록이 자란다"만 했다. 이벤트를 눌러 재생 위치를 옮기는 것은 하지 않았다.
- T1.10.2의 "콘솔에 실패 사유 표시"는 하지 않았다. 콘솔은 지금처럼 OS 출력만 보인다.
