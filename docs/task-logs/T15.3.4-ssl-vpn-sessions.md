## 2. 진행 방식

기존 Goorm 미커밋 전송 기반을 보존한 상태에서 새 브랜치를 만들었다. 공유 설정 계약 → reducer → Router TCP endpoint → Runtime 세션 관리자 → PC CLI → 실습 예제·화면 이벤트 순서로 연결했다.

서버 정보를 받기 전에 인증 식별자를 보내지 않는다. 서버 이름·CA 식별자·가상 인증서 만료를 먼저 검사하고, 사용자 일치 검사 후 IP offer/confirm/ready를 주고받는다. 마지막 ready가 실제 수신되기 전에는 세션과 IP 할당을 확정하지 않는다. 모든 제어 메시지는 ARP·라우팅·케이블·방화벽을 거친다.

### 주요 결정

| 결정 | 이유 | 대안 |
|---|---|---|
| 실제 TLS 대신 공개 식별자 교육용 검사 | 합의된 시뮬레이션 범위 유지 | 실제 인증서·암호화·비밀번호 저장 |
| 가상 수명과 수동 상태 확인 시 만료 정리 | 결정적인 테스트와 기존 커널 시간 사용 | 현실 시간 타이머 |
| VPN trace 종류 추가 | ping 성공으로 오해하지 않도록 표시 | ping 이름으로 표시 |
| 설정/링크·물리 포트 변경 시 재접속 요구 | 오래된 세션을 계속 유효하게 보이지 않게 함 | 무조건 연결 유지 |

## 4. 결과와 검증

```text
VITEST_MAX_WORKERS=2 pnpm check
  lint / typecheck: 통과
  scripts 35 / shared 458 / engine 1928 / web 587 / api 2 passed
  총 3010개 테스트, Vitest 142개 파일 통과
  shared / engine / web / api build: Done
pnpm check:secrets
  추적 파일 787개 통과
  신규 미추적 파일 16개: 같은 검사 함수로 검사, 0건
```

새 엔진 세션 테스트 21개, 웹 세션 테스트 3개가 통과했다. 정상 6개 제어 메시지 각각 ISP·Firewall 경유를 확인하고, 잘못된 이름/CA/사용자/authId, 요청/응답 방화벽 차단, 가상 만료, 최대 4개 세션·IP 고갈·해제 후 재사용, 저장 후 세션 미복구, 기존 help/Tab/ipconfig를 확인했다. 내부 PC ping은 아직 실패하는 것을 명시적으로 검사한다.

전체 검사에서 PC 도움말 명령 목록의 기존 예상 값이 새 명령 3개를 포함하지 않아 한 번 실패했고, 실제 등록된 명령 목록과 일치하도록 수정한 뒤 전체 검사를 통과했다. 기존 Vite chunk-size 경고는 남아 있으며 빌드는 성공했다.

수동 브라우저 검증은 완료하지 못했다. 사용 중인 Chrome 창 조작을 중단하고 별도 브라우저를 시도했으나 호스트를 사용할 수 없었다. 대신 실제 Simulator trace로 서버 렌더링한 이벤트 패널과 재생 분류를 자동 검증했다. Goorm apps/web에서 동작 중인 5175 서버와 실습 URL의 HTTP 200 응답도 확인했다. 직접 실행 경로는 [실습 안내](../guides/ssl-vpn-implementation-status.md)에 적었다.

## 5. 추정과 실제

인일 추정은 하지 않았다. 이전 TCP 전달 기반에 이어 설정·접속·세션 단계를 한 작업으로 묶었다.

## 6. 계획과 달라진 점

제안 계획의 설정 계약과 세션·PC 접속 CLI를 함께 구현했다. 내부 패킷 데이터 터널과 설정 UI는 다음 단계다. 본 작업의 connect/disconnect/status는 PING9 전용이며 실제 VyOS SSL VPN 명령어를 구현했다고 표시하지 않는다. 팀 공식 계획 문서는 변경하지 않았다.
