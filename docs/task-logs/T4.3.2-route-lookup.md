## 2. 진행 방식

활성 RoutingEntry 배열과 목적지 IP를 받는 순수 함수 lookupRoute를 추가했다. 결과는 선택된 경로·출력 포트·ARP 대상(nextHop)이다. 직접 연결 경로의 ARP 대상은 최종 목적지이며 정적 경로는 설정한 다음 홉이다.

같은 길이의 정적 경로가 여러 개이면 작은 다음 홉 IPv4 값, 포트 이름 순으로 선택한다. 입력 순서를 바꿔도 같은 결과이며 ECMP나 재귀 해석은 하지 않는다. 함수는 배열이나 경로 객체를 수정하지 않는다.

### 주요 결정

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| 활성 경로 배열을 입력으로 받음 | Runtime/DeviceModel 통합 전에도 독립 검증·재사용 가능 | 함수 안에서 프레임 전송까지 수행 |
| 선형 조회 | Router당 정적 경로가 100개로 제한됨 | 트리·별도 캐시 관리 |
| CLI에 show ip route 목적지 추가 | 브라우저 터미널에서도 선택 결과 확인 | 내부 테스트에서만 결과 확인 |

## 4. 결과와 검증

세 작업을 합친 최종 트리에서 Node 24.19.0으로 실행했다.

```text
pnpm check
lint / typecheck / build 통과
scripts 35 + shared 311 + engine 1283 + web 301 + api 2 = 1932 tests passed
pnpm check:secrets
추적 파일 563개 통과
```

- 무작위 목적지·경로 1,000건을 숫자 주소 구간 기반의 별도 기준과 비교했다. 최장 접두사와 직접 연결 우선이 같고, 배열을 뒤집어도 결과가 같았다.
- /0, /16, /24, /32 중 선택, 서브넷 처음/끝 주소, 부호 비트가 켜진 주소, 불일치·빈 테이블·잘못된 주소를 검사했다.
- 동일 길이에서 직접 연결 우선, 직접 연결보다 더 구체적인 정적 경로 우선, 다음 홉의 숫자 비교(.2 < .10), 원본 배열 보존을 검사했다.
- 두 Router의 연결과 포트 상태를 구성한 뒤 CLI로 정적 경로를 설정했다. 목적지 조회의 다음 홉·출력 포트를 확인하고, 링크를 끊으면 경로 없음으로 바뀌는 것까지 검사했다.

CLI에서 확인:

```text
R1# show ip route
R1# show ip route 192.168.2.10
Routing entry for 192.168.2.0/24
  S - static
  Next hop: 10.0.12.2
  Outgoing interface: GigabitEthernet0/0
```

위 결과의 전제는 R1 Gi0/0이 10.0.12.1/30로 실제 up이며, `ip route 192.168.2.0 255.255.255.0 10.0.12.2`가 설정된 상태다. 다음 홉 장비의 실제 수신 성공까지 의미하지는 않는다.

## 6. 계획과 달라진 점

- 실제 IPv4 전달(T4.2.1) 없이 경로 선택을 먼저 구현했다. 실제 포트 전송·TTL·MAC 변경은 이번 범위에 없다.
- 확인용 CLI 목적지 조회와 정적 경로 동률의 결정 규칙을 추가했다. 계획 문서 본문은 수정하지 않았다.
- 공통 모델 PR #33의 DeviceModel 계약을 확인했으며, 이 계산 함수들은 이후 Router 모델에서 재사용한다. 현재 문서 기반 스냅샷과 CLI에만 연결했다.
