## 1. 목표와 완료 기준

담당의 결정(2026-11-19): **기존 Firewall 장비를 없앤다. `iptables` 명령은 서버에 넣는다.** PC의 종류에서 Server를 고르면 그 PC의 콘솔에서 `iptables`가 그대로 동작한다.

2026-11-16의 결정("별도 장비로 만든다", T14.2.1)을 사흘 만에 뒤집는 것이다.

- [x] 장비 종류 `firewall`이 없다: 장비 목록, 아이콘, 모델, 콘솔, 구성 형태, 뷰에서 모두 뺐다
- [x] 종류가 Server인 PC의 콘솔에서 `iptables`가 동작한다. T14.2.1의 문법 그대로다: `-A`, `-I`, `-D`, `-F`, `-P`, `-L`, `-S`, 조건 `-p`, `-s`, `-d`, `-i`, `-o`, `--icmp-type`, `--sport`, `--dport`, 대상 `ACCEPT`·`DROP`·`REJECT`. 앞에 `sudo`를 붙여도 된다
- [x] 규칙이 실제 패킷을 거른다. INPUT은 서버로 온 패킷, OUTPUT은 서버가 보내는 패킷이다. ping과 T0.20의 HTTP·DNS·NTP·FTP 요청이 모두 걸린다
- [x] 막힌 패킷의 추적에 어느 체인의 몇 번 규칙(또는 기본 정책)이 막았는지 남고, "실패한 이유"에 보인다 (Story 14.3 그대로)
- [x] Windows·Linux PC에는 `iptables`가 없다. 종류를 Server에서 바꾸면 규칙은 문서에 남지만 적용되지 않고, 다시 Server로 고르면 그대로 적용된다
- [x] 서버의 속성 패널에 "필터 규칙 (iptables)" 구역이 보인다
- [x] 팀원이 만든 방패 장면([T14.2.3](T14.2.3-firewall-scene.md))을 지우지 않고 서버로 옮겼다: 규칙을 건 서버는 방패 배지를 달고, 허용·DROP·REJECT 장면이 서버에서 나온다
- [x] Firewall 장비가 든 옛 파일을 열 수 있다 (Router로 바뀐다. 6절)
- [x] 공통 완료 조건: lint, 타입 검사, 단위 테스트, 빌드 (4절)
- [ ] 리뷰 — 아직 PR을 올리지 않았다

## 2. 진행 방식

1. `firewall`이 쓰이는 곳을 모두 찾았다 (소스 55개 파일). `shared` → `engine` → `web` 순서로 고치고, 단계마다 타입 검사와 그 패키지의 테스트를 돌렸다.
2. `shared`: 장비 종류에서 `firewall`을 빼고, 규칙을 PC 구성의 `filter` 칸으로 옮겼다. 규칙의 형태(`FirewallRule`)와 검사 함수는 그대로 두고 대상만 바꿨다.
3. `engine`: Firewall의 모델·콘솔·경로 처리를 지웠다. 필터 판정(`filter.ts`)과 `iptables` 해석기는 옮겨서 그대로 쓴다. 호스트의 IPv4 처리(`ipv4-host.ts`)에 INPUT·OUTPUT 검사를 넣었다.
4. `web`: 장비 목록·아이콘·이름표에서 Firewall을 빼고, 필터 규칙 구역과 방패 장면을 서버에 붙였다.
5. 지운 테스트(Firewall 장비 기준 4개 파일)를 서버 기준으로 다시 썼다.
6. 개발 서버를 띄워 브라우저에서 실습을 손으로 했다 (4절).
7. 독립 검토(읽기 전용)를 돌려 나온 것을 고쳤다 (4절).

### 주요 결정

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| 규칙은 PC 구성의 `filter` 칸에 둔다. **종류가 Server일 때만** 적용한다 (`filterOf`) | 담당의 결정. 서비스(`services`)와 같은 방식이라 종류를 잠깐 바꿨다 돌아와도 규칙이 남는다 | 종류를 바꿀 때 지우기. Linux PC에도 `iptables` 주기: 요청은 "server 선택하면"이다 |
| 서버는 포트가 하나이고 패킷을 전달하지 않는다. **INPUT과 OUTPUT만 패킷을 본다.** FORWARD는 규칙을 넣고 볼 수 있지만 맞는 패킷이 없다 | 실제 Linux 호스트의 방화벽과 같다. FORWARD를 막으면 실제 `iptables`를 아는 사람의 명령이 오류가 난다 | FORWARD 체인을 없애기 |
| **두 네트워크 사이에서 거르는 실습은 없어졌다** | 서버는 Router가 아니다. 전달하는 장비에 필터를 두려면 Router에 넣어야 하고, 그것은 Router 담당과 정할 일이다 | 서버에 포트를 늘려 전달하게 하기: PC가 Router가 된다 |
| Command 이름(`firewall/add-rule` 등 4개)과 코드(`FIREWALL_*`, `IPTABLES_*`)는 그대로 | 의미가 같고(방화벽 규칙), 바꾸면 고칠 곳만 는다. 대상만 서버 PC로 바뀌었다. 서버가 아니면 `PC_NOT_SERVER` | `pc/filter-*`로 이름 바꾸기 |
| Firewall의 인터페이스·경로 Command 처리(`interface/set-ip` 등이 Firewall도 받던 것)는 지웠다 | 그 장비가 없다 | — |
| 인터페이스 이름은 `eth0`(`Ethernet0`) 하나. `-i eth1`은 받지 않는다 | 서버의 포트가 하나다 | — |
| `-i lo`, 상태 추적(`-m state`), NAT, 사용자 체인, `!` 부정은 전처럼 `IPTABLES_UNSUPPORTED` | T14.2.1의 범위 그대로 | — |
| ARP는 거르지 않는다 | 실제 `iptables`도 ARP를 보지 않는다. 모든 것을 DROP해도 주소 풀이는 된다 | — |
| REJECT는 ICMP 도달 불가를 돌려준다. ICMP 오류와 TCP RST에는 답하지 않는다 | T14.2.1과 같다. 오류에 오류로 답하면 돈다 | — |
| 서버 콘솔에서는 앞의 `sudo`를 떼고 실행한다 | 실제 서버에서는 `sudo iptables …`로 친다. 따라 치는 실습 문서가 그대로 동작한다 | `sudo`를 오류로 두기 (Linux PC는 지금도 `sudo: command not found`) |
| **옛 파일의 Firewall 장비는 Router로 바꿔 연다.** 인터페이스 주소·Static route·케이블은 남고, 포트 이름은 `EthernetN` → `GigabitEthernet0/N`, **필터 규칙은 버린다** | 파일을 못 여는 것보다 낫다. 전달하던 장비이므로 Router가 가장 가깝다. 변환은 `migrateDocument`가 한다 (가져오기와 저장한 문서 읽기가 함께 쓴다) | 열기를 거부하기. 서버 PC로 바꾸기: 포트가 넷에서 하나가 되어 케이블이 끊긴다 |
| 방패 장면(T14.2.3)을 서버로 옮겼다. 규칙이 걸린 서버는 이글루 오른쪽 위에 방패 **배지**를 단다 | 팀원이 만든 장면을 버리지 않는다. 평소에 배지가 있어야 허용·차단으로 바뀌는 것이 보인다 | 장면을 지우기 |
| 허용 방패는 **지금 규칙을 건 서버가 패킷을 받아들이거나 내보낼 때**, 차단 방패는 **추적에 `FIREWALL_BLOCKED`가 있을 때** | 허용은 규칙이 없으면 보일 것이 없다. 차단은 그 뒤에 규칙을 지웠어도 그때는 막았다 | 둘 다 지금의 구성으로 판단 |
| 재생 단계의 `forwarded`·`passesAt`(Firewall이 넘긴 프레임)을 빼고 `acceptedBy`(프레임을 받아들인 장비들)를 넣었다 | 서버는 넘기지 않고 받는다. 앞의 둘은 방패 장면만 쓰고 있었다 | — |

### 브라우저에서 직접 (개발 서버, 1280×800)

1. 장비 목록에 PC, Switch, Router만 있다.
2. PC 둘을 놓고 PC2의 OS에서 **Server**를 고르고 케이블을 이었다. PC1 `ipconfig 10.0.1.10 255.255.255.0`, 서버 `sudo ip addr add 10.0.1.20/24 dev eth0`.
3. 서버에서 `iptables -L` → 세 체인 모두 `policy ACCEPT`. PC1의 `ping -n 1 10.0.1.20` → `Reply from 10.0.1.20`.
4. `iptables -A INPUT -p tcp --dport 80 -j DROP` → 서버 아이콘 오른쪽 위에 방패 배지가 생기고, 패널의 "필터 규칙 (iptables)"에 `1 -p tcp -m tcp --dport 80 -j DROP`이 보인다. ping은 계속 된다.
5. `iptables -A INPUT -p icmp -j REJECT` → PC1의 ping이 `Reply from 10.0.1.20: Destination net unreachable.` `iptables -nL INPUT --line-numbers`에 두 줄.
6. 시뮬레이션 모드에서 REJECT를 지우고 `iptables -A INPUT -p icmp -j DROP` 뒤 ping → 펭귄이 서버 앞에서 흩어지고 방패가 빨간 X와 "규칙 2 차단". 그 규칙을 지우고 ping → 방패가 초록 체크와 "허용".

### 독립 검토 (읽기 전용 하위 작업)

막는 길목(INPUT·OUTPUT이 한 번씩, ARP 앞에서), REJECT가 돌지 않는지, reducer에 넣은 이상한 값 26가지, 종류·주소·서비스·이름을 바꿔도 규칙이 남는지, 남은 `firewall` 참조는 문제없다고 봤다. 나온 것:

| 나온 것 | 처리 |
|---|---|
| REJECT한 서버가 보낸 쪽의 MAC을 몰라 ARP부터 하면, ARP 펭귄이 뒤집혀 걷고 정작 ICMP 오류 펭귄은 "허용" 방패 아래로 나갔다 | 고침. 막은 이벤트를 ARP 이벤트를 건너 찾고, ICMP 오류에만 붙인다 (`steps.ts`의 `rejectedBy`) |
| 다른 곳에서 먼저 실패한 뒤 서버의 필터가 버린 패킷(원인 폐기가 아님)에는 방패가 반응하지 않았다 | 고침. 방패가 빨개지고 펭귄의 이름표가 "iptables 규칙이 막음"이다 |
| 옛 Firewall의 구성에 없는 인터페이스는 켜진 것이었는데 Router로 바꾸면 꺼진 것이 됐다 | 고침. 없는 인터페이스를 `adminUp: true`로 채운다. 인터페이스 표에 Firewall의 것이 아닌 이름이 있으면 바꾸지 않고 거부한다 |
| 서버 콘솔의 Tab이 `sudo ipt`를 완성하지 못했다 | 고침 |
| 주석 하나(RIP), 쓰지 않는 export 하나 | 고침 |
| 서버가 자기 주소로 보낸 요청은 필터를 지나지 않는다 | 고치지 않음. 지금 동작을 테스트로 못 박고 7절에 적었다 |
| OUTPUT이 막은 ping이 시간 초과로 보인다 (실제는 `Operation not permitted`). REJECT된 ping의 문구가 `Net Unreachable`이다 | 고치지 않음. PC 담당의 ping 결과 종류를 늘려야 한다 (7절) |

## 6. 계획과 달라진 점

- **Firewall 장비가 없다.** 요구사항 F1("Firewall 장비: 무상태 패킷 필터")과 Story 14.2("Firewall을 놓고 인터페이스 방향별 규칙을 건다")는 장비를 전제로 한다. 지금은 서버의 호스트 방화벽이다. 인터페이스 방향(`-i`, `-o`)은 문법으로 남아 있지만 포트가 하나라 고를 것이 없다. 계획 문서 본문은 팀이 합의한 뒤에 고친다.
- **두 네트워크 사이를 지나는 트래픽은 거를 수 없다.** T14.2.1의 실습(PC — Firewall — PC, FORWARD 체인)이 없어졌다. Story 14.1(확장 ACL)로 Router에 넣는 것이 남은 길이다.
- **T14.2.1, T14.2.2, T14.2.3의 결과가 바뀌었다.** T14.2.1의 장비는 사흘 만에 없어졌고, T14.2.2(Firewall의 GRE·ESP 통과)는 고칠 대상이 사라져 코드와 테스트를 지웠다. T14.2.3(yysong1249)은 Firewall 그림을 지우고 방패와 장면만 서버로 옮겼다 — **담당의 확인이 필요하다.**
- **담당이 아닌 파일을 고쳤다.** PC(yysong1249)의 `ipv4-host.ts`·`pc-model.ts`·`console.ts`·`pc-set-ip.ts`, 화면의 `packet-layer.tsx`·`steps.ts`·`device-icons.tsx`·`canvas.tsx`, Router(ssunyoung2)의 `router-inspector.tsx`(Firewall과 함께 쓰려고 넓혔던 타입을 되돌림).
- **`shared`의 문서 형태가 바뀌었다** (`DEVICE_KINDS`, `PcConfig.filter`). `schemaVersion`은 올리지 않았다: 옛 문서는 `migrateDocument`가 바꾸고, 새 칸은 선택이다.
- **옛 파일의 Firewall은 Router가 되고 규칙은 사라진다.** 이름(`FW1`)은 그대로 남는다. 운영 DB에 저장된 문서도 읽을 때 같은 변환을 거친다.

## 7. 남은 일과 다음 Task에 전할 것

- PR, 팀원 검토. T14.2.3 담당(yysong1249)에게 방패 배지의 자리와 크기를 보여 줄 것.
- 계획 문서(02의 F1, 04의 E14)를 팀과 맞춰 고칠 것.
- 서버가 **자기 주소**로 보낸 요청(`curl 127.0.0.1`, 자기 IP)은 필터를 지나지 않는다. 실제 Linux는 `lo`로 OUTPUT과 INPUT을 지난다. `-i lo`도 받지 않는다.
- REJECT의 `--reject-with`는 고를 수 없다. Windows의 ping은 REJECT를 `Destination net unreachable.`로 찍는다 (ICMP 도달 불가의 코드를 나누지 않는다. T14.2.1부터 같다).
- OUTPUT이 막은 ping은 시간 초과로 보인다. 실제 Linux는 바로 `ping: sendmsg: Operation not permitted`를 찍는다. ping 결과의 종류(`shared/ping.ts`)를 늘려야 해 PC 담당과 정할 일이다.
- 허용 방패는 재생하는 때의 규칙으로 판단한다 (차단 방패는 추적으로). 재생 중에 규칙을 바꾸면 허용이 어긋날 수 있다.
- 속성 기반 테스트(`simulator.property.test.ts`, `validate.property.test.ts`)가 규칙 Command, 서버 PC, `filter` 값을 만들지 않는다.
- 상태 추적이 없어 `OUTPUT`을 DROP으로 두면 응답도 나가지 못한다. 응답을 허용하려면 `--sport`로 열어야 한다 (`iptables -A OUTPUT -p tcp --sport 80 -j ACCEPT`).
- 두 네트워크 사이의 필터가 필요하면 Router에 ACL을 넣는 Task를 새로 잡는다 (Story 14.1).
