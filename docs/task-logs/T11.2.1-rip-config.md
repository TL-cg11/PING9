- [x] 명령어로 넣은 RIP 구성이 문서에 저장된다 (`RouterConfig.rip`)
- [x] `show running-config`에 `router rip` 묶음이 나오고, 그 출력을 새 Router에 넣으면 같은 구성이 된다 (왕복)
- [x] `config-router` 모드: 프롬프트 `R1(config-router)#`, `exit`는 `config`로, `end`는 `privileged`로
- [x] 오류: `version 1`, `auto-summary`, 넣을 수 없는 주소, 없는 네트워크 지우기, 17개째 `network`, RIP를 켜기 전에 설정하기
- [x] `rip`이 없는 옛 문서는 그대로 읽힌다 (`schemaVersion`을 올리지 않음)
- [x] 공통 완료 조건: lint, 타입 검사, 단위 테스트, 빌드 (4절). 리뷰는 PR에서

## 2. 진행 방식

1. E11 설계안(팀 합의 전 초안)에서 다른 Task와 상관없이 먼저 할 수 있는 이 Task를 골랐다. 경로 계산, 패킷 전달과 상관없고, 나머지 E11 Task가 모두 "RIP가 켜진 Router"를 전제로 한다.
2. 고치는 파일이 PR #40(Router)과 많이 겹쳐 PR #40 브랜치에서 시작했다. PR #40이 병합된 뒤 `main` 위로 옮겼다. 충돌은 없었다.
3. 데이터와 검증: `RipConfig`, Zod 형태, `checkRipConfig`(클래스풀, 한도, 포트 이름), `normalizeRipConfig`(정렬).
4. Command 5개와 reducer(`reducer/router-rip.ts`). 클래스풀로 맞추는 일은 reducer가 한다. 나중에 설정 패널도 같은 Command를 내므로 결과가 같다 (AD-3).
5. CLI: `config-router` 모드와 명령어(`cli/router/rip-commands.ts`), `show running-config`의 `router rip` 묶음.
6. 테스트: 클래스풀 경계값, reducer 성공·거부, 문서 검증, 모드, 명령어, 무작위 구성 40개로 왕복(fast-check).

### 주요 결정

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| `network`는 클래스풀 네트워크로 맞춰 저장 (`10.0.1.0` → `10.0.0.0`) | 실제 IOS와 같다 | 넣은 그대로 저장 |
| `version 2`, `no auto-summary`는 저장하지 않음 | 늘 그 값이다 (E11 설계안 결정 5). `show running-config`에는 실제처럼 나온다 | 문서에 칸을 둠 |
| `version 1`, `auto-summary`는 오류 | 받아 두고 실제로는 안 하면 사용자가 그렇게 동작한다고 착각한다 | 받고 무시 |
| `network` 16개 한도 (`LIMITS.maxRipNetworks`) | 문서 크기를 막는 다른 한도들과 같은 취지. 실제 IOS에는 없다 | 한도 없음 |
| 없는 네트워크를 `no network`로 지우면 오류 `RIP_NETWORK_NOT_FOUND` | Static의 `ROUTE_NOT_FOUND`와 같은 취지 | 조용히 무시 |
| 이미 그 상태인 Command는 같은 문서 객체를 돌려줌 | 화면이 다시 그려지지 않고, 기록에 바뀐 것 없는 줄이 남지 않는다 | 새 객체 |
| `passive-interface default`는 넣지 않음 | 이번 범위가 아니다. 필요하면 T11.2.2 뒤에 | 함께 넣음 |

## 6. 계획과 달라진 점

- 계획(04 문서 4.9절)에는 E11의 Task 분해가 없다. `T11.2.1`은 이 작업에서 정한 ID다.
