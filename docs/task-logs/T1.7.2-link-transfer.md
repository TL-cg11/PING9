## 2. 진행 방식

`link.test.ts`와 `topology.test.ts`를 먼저 쓰고(모듈이 없어 실패) 구현을 만들었다. 테스트는 진짜 kernel(`createKernel`) 위에서 가짜 장비 모델 둘로 돈다.

이 Task 앞에 kernel(T1.7.1), ARP(T1.8.1, PR #30), IPv4·ICMP(T1.8.2, PR #32), Switch 전달 규칙(T1.7.3)이 먼저 만들어졌고, 그 기록 문서들이 T1.7.2에 바라는 것을 적어 두었다. 그에 맞춰 만들었다:

- kernel의 `SimContext.sendFrame(target, frame, delayUs, parentSeq?)`은 "수신 포트와 지연을 명시적으로 받는 내부 예약 함수"이고 링크 유효성은 보지 않는다. 그래서 `transmit`이 링크 상대를 찾고 `LINK_DELAY_MICROSECONDS`를 넘긴다.
- ARP의 `ArpHost.transmit(ctx, port, frame)`은 "링크 상대 찾기, 지연, 링크 없음 폐기는 T1.7.2가 한다"고 되어 있다. PC 모델(T1.8.3)이 `ArpHost.transmit`을 이 `transmit(ctx, document, { deviceId, port }, frame)`으로 채우면 된다.
- Switch 전달 규칙은 받는 쪽에서 `IF_DOWN`을 낸다. 그래서 링크 계층은 상대 포트의 상태를 보지 않는다.

### 주요 결정

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| 링크 계층은 이벤트를 기록하지 않는다 (폐기만) | 예시 `twoPcPingTrace`에서 보냄(seq 0, `outPort`·`linkId`)과 받음(seq 1)은 장비의 ARP·ICMP 이벤트다. 링크 이벤트를 따로 넣으면 예시와 달라진다 | "링크를 지나감" 이벤트 추가 |
| 보내는 쪽 포트가 꺼져 있으면 `IF_DOWN`, 링크가 없으면 `NO_LINK`. 상대 포트는 보지 않는다 | 꺼진 포트에서는 프레임이 나갈 수 없다. 상대가 꺼진 경우는 받는 장비가 자기 포트 상태로 판단하는 것이 `switchForward`(T1.7.3)와 맞고, 폐기가 어느 장비의 어느 포트 때문인지 그대로 드러난다 | 상대 포트가 꺼져 있으면 보내는 쪽에서 폐기 (params에 상대 포트를 담을 자리가 없다) |
| `transmit(ctx, document, from, frame, parentSeq?)`는 함수 하나. 문서를 매번 받는다 | 한 회차 동안 Document는 바뀌지 않고, 상태가 없어 모델 사이에서 공유할 객체가 필요 없다 | 문서를 들고 있는 `LinkLayer` 객체 |
| `DeviceModel.onConfigChanged(change)`에 `SimContext`를 주지 않는다 | 구성 변경은 kernel 실행 밖(dispatch)에서 일어나고, kernel의 `SimContext`는 콜백 안에서만 유효하다 (T1.7.1 규칙) | 설계 문서 그대로 `(ctx, change)` |
| `ConfigChange`는 바뀌기 전·후 Document 둘 | `pruneMacTable`(T1.7.3)이 이전 구성을 받아 모드가 바뀐 포트의 항목을 지우고, ARP의 `onPortChanged`는 IP·링크 변화를 비교해야 한다. 변경 종류를 열거하는 것보다 모델이 직접 비교하는 쪽이 모델마다 다른 관심사에 맞다 | 변경 종류 열거형 |
| `deviceRun`으로 kernel 사건을 모델에 넘기고, 모델이 없으면 예외 | 모델 목록과 문서가 어긋난 것은 내부 오류다. kernel도 내부 위반을 예외로 알린다 | 조용히 버림 |
| `views.ts`의 `isAdminUp`과 링크 찾기를 `topology.ts`로 옮겨 함께 쓴다 | 포트 상태(화면)와 링크 전달(엔진)이 "포트가 켜져 있는가", "링크 상대는 누구인가"에 같은 답을 내야 한다 | 두 벌로 둠 |

## 6. 계획과 달라진 점

- **`Frame`, `FrameSnapshot`, MAC 주소 계산 함수는 새로 만들지 않았다.** T1.2.1(`FrameSnapshot`), T1.2.4(`macAddressFor`), T1.7.1(`Frame`)에 이미 있다. 이 Task는 그 위에 `DeviceModel`, 링크 전달, 폐기만 더했다.
- **`IF_DOWN` 폐기를 함께 넣었다.** 계획의 세부 작업은 "링크가 없을 때의 폐기"만 적었는데, T1.7.1 기록 7절이 "연결이 없거나 포트가 꺼졌으면 기존 폐기 코드를 기록한다"고 넘겼다.
- **`DeviceModel.onConfigChanged`에 `SimContext`가 없다.** 03 문서 3.4절은 `onConfigChanged(ctx, change)`다. 이유는 2절의 결정 표.
- **순서:** 계획은 T1.7.2 → T1.8.1 → T1.8.2이지만 ARP와 IPv4·ICMP가 가짜 `transmit`으로 먼저 나왔다. 이 Task는 그 모듈들이 요구한 모양에 맞췄다.

## 7. 남은 일과 다음 Task에 전할 것

- **T1.8.3 (PC 모델, `ping`):** `DeviceModel`을 구현한다. `ArpHost.transmit(ctx, port, frame)`은 `transmit(ctx, document, { deviceId, port }, frame)`을 부르면 된다. `macOf`는 `portMac(device, port)`, `linkOf`는 `portLink(document, ref)?.linkId`. `onConfigChanged`에서는 두 문서를 비교해 IP가 바뀌었거나 링크가 지워진 포트에 `ArpModule.onPortChanged(port)`를 부른다.
- **T5.2.2 (Switch 모델):** `switchForward`의 `outputs`마다 `FRAME_FORWARDED`/`FRAME_FLOODED`를 기록한 뒤 그 seq를 `parentSeq`로 `transmit`을 부른다 (flooding은 형제 이벤트끼리 이어지지 않도록 부모를 명시한다 — T1.7.1 기록 7절 5번). `isPortUp`은 `computeViews` 결과가 `up`인지. `onConfigChanged`에서 `pruneMacTable(table, { config, isPortUp, previousConfig })`.
- **Simulator 연결** (`load`에서 kernel `reset()`, 장비 모델 생성, `dispatch` 뒤 `onConfigChanged`, `ping`에서 `run(deviceRun(...))`, Trace 보관)은 아직 없다. T1.8.3에서 `ping`을 만들 때 함께 넣는 것이 자연스럽다.
- **알려진 어긋남:** `transmit`에 `parentSeq`를 주지 않으면 `NO_LINK`·`IF_DOWN` 폐기 이벤트의 부모는 kernel `record`의 기본값(이 처리를 일으킨 사건)이고, 바로 앞의 보냄 이벤트(`ARP_REQUEST_SENT` 등)가 아니다. ARP는 `transmit`에 seq를 넘기지 않으므로, 첫 회차에서 링크가 없으면 보냄과 폐기가 부모 없이 나란히 놓인다. 고치려면 `ArpHost.transmit`에 `parentSeq`를 더하거나 kernel `record`의 기본 부모를 예약과 같은 "마지막 기록"으로 바꿔야 한다. 둘 다 다른 사람의 모듈이라 손대지 않았다.
- `peer-down`인 포트로 내보낸 프레임은 상대 장비에 도착한다. PC는 포트를 끌 수 없어 해당 없고, Switch는 `switchForward`가 `IF_DOWN`을 낸다. Router 모델(E4)도 받은 포트가 꺼져 있으면 `IF_DOWN`을 내야 한다.
