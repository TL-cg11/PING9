## 2. 진행 방식

1. 예시 자료 `two-pc.ts`를 먼저 읽고 설계와 맞췄다. PC 2대 직결이라 Switch 모델(T1.7.3) 없이 비교할 수 있다. `twoPcSnapshot`은 "첫 회차 직후"라 추적이 1개뿐이어서, 스냅샷 비교는 `ping -n 1`로 한다.
2. T1.7.2(PR #33)는 11-06의 main에서 갈라져 ARP·IPv4·PC OS가 없다. 그래서 #33 브랜치에서 이 브랜치를 만들고 main을 합쳤다 (충돌 없음, 커밋 `Merge main into feat/T1.8.3-pc-ping`).
3. PC 모델 → Runtime → Simulator 연결 → 명령어 → 출력 순으로 만들고, 공개 인터페이스(`createSimulator`)로 통합 테스트를 썼다. 예시 자료 세 개는 처음 실행에서 그대로 같았다.

### 주요 결정

설계 문서(로컬 설계안 10절)에서 사용자와 정한 것을 따랐다.

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| PC 모델은 구성을 복사하지 않고 매번 Document에서 읽는다. 들고 있는 것은 ARP 테이블뿐 | IP·이름·OS가 바뀌어도 모델을 다시 만들 필요가 없다 | dispatch마다 모델을 새로 만들기 (ARP 테이블이 사라짐) |
| Runtime(`runtime.ts`)을 Simulator와 따로 둔다. kernel, PC 모델, 추적 보관 | Simulator는 공개 경계만 남기고, 실행 상태는 한곳에서 | Simulator 안에 모두 |
| 명령어는 `CommandContext.runtime`(선택 값)으로 Runtime을 쓴다 | `ping`, `arp -d`는 Document를 바꾸지 않으므로 dispatch로 가지 않는다 (03 문서). 선택 값이라 기존 테스트와 Switch·Router 명령은 그대로 | 명령 해석기 밖에서 ping을 따로 처리 |
| ping 횟수는 기본 4, `-n`/`-c` 1~10. Linux도 기본 4로 끝낸다 | 콘솔에 Ctrl+C가 없고 결과가 한 번에 나온다. 추적은 20개만 보관 | Linux처럼 끝없이, `-t` |
| 자기 IP와 127.x는 링크 없이 성공 줄만, 추적 없음 | 실제 OS도 랜카드 밖으로 내보내지 않는다. 재생할 링크가 없다 | 장비 안에서만 도는 짧은 추적, 거부 |
| Windows의 ARP 실패는 실제처럼 `Reply from <자기 IP>: Destination host unreachable.`, "받음"으로 센다 | 실제와 같게 (사용자 결정) | `Request timed out.`으로 단순하게 |
| Linux에서 보내지 못하면 `ping: connect: Network is unreachable` 한 줄로 끝내고 첫 회차의 추적만 붙인다 | 실제 출력은 그대로 두면서 실패 회차의 추적을 열 수 있게 (FR-38) | 추적 없이 한 줄만 |
| 왕복 시간 요약 줄(Windows `Approximate…`, Linux `rtt …`, `time 3004ms`)은 넣지 않는다 | 예시 자료에 없고, 가상 시간이라 뜻이 작다 | 넣고 예시 자료도 고치기 |
| Switch·Router를 지나는 ping은 `PING_DEVICE_UNSUPPORTED` 오류 한 줄, 그 ping의 추적은 남기지 않는다 | 모델이 아직 없다. 조용히 버리는 임시 모델은 평범한 실패로 보여 학습자가 자기 설정이 틀렸다고 잘못 배운다 | 아무것도 안 하는 임시 모델, 예외로 콘솔이 깨짐 |
| 결과 분류는 Trace를 읽어서 한다: 응답 받음 → `NO_IP`/`NO_GATEWAY` 폐기 → 출발 PC의 `ARP_TIMEOUT` → 나머지는 타임아웃 | T1.8.2 모듈을 고치지 않는다. 시간과 TTL도 받은 응답 이벤트의 값 | 모듈이 결과를 따로 돌려주게 고치기 |
| `ARP_TIMEOUT`은 "주 폐기"가 아니어도 본다 | 링크가 없으면 첫 폐기는 ARP 요청의 `NO_LINK`이고 `ARP_TIMEOUT`은 뒤에 온다. 실제 Windows도 이때 `Destination host unreachable` | `primaryDropSeq`의 코드만 보기 |

새 테스트(`ping.test.ts`, `ping-output.test.ts`)가 확인하는 것:

- 예시 자료: `ping 192.168.1.2` 결과 = `twoPcPingConsoleResult`, `getTrace(1)` = `twoPcPingTrace`, `ping -n 1` 뒤 스냅샷 = `twoPcSnapshot`. 2회차는 ARP 없이 ICMP 4개. 두 번 실행해도 같은 추적 (AD-5)
- Windows 실패: 링크 없음·없는 주소 → `Destination host unreachable.`, 받음으로 셈 / 응답이 안 돌아옴 → `Request timed out.` / IP 없음·게이트웨이 없음 → `General failure`
- Linux: 형식, 응답한 쪽의 TTL(128), 보내는 TTL 64, 기본 4회, `From … Destination Host Unreachable`와 `+N errors`, `no answer yet`, 보내지 못하면 한 줄 + 추적 하나
- 거부: 브로드캐스트 두 종류(추적·`runtimeVersion` 그대로), IP 형식, 횟수 0·11, `-t`
- 자기 IP·127.0.0.1: 추적 없이 성공, 스냅샷 그대로
- Switch를 지나는 ping: 오류 한 줄, 추적 없음, 그 뒤 다른 ping은 됨
- ARP: `arp -a`, `arp -d`, `arp -d <IP>`, `arp -d *`, 상대 PC와 패널 값, Linux `ip neigh`·`flush all`·`arp -a`·`arp -d`, IP 변경·링크 삭제 시 비움, 위치 이동은 그대로, `load`가 비움
- 추적 보관: 최근 20개, 요약의 값
- 출력 규칙: Linux 시간 표기(0.030, 4.00, 12.3, 123), 손실률(Windows 66%, Linux 66.6667%), `time<1ms`

화면에서 직접 실행해 보지는 않았다. web 콘솔은 추적 줄을 아직 그리지 않는다 (T1.9.4).

- 06 문서는 P2에서 `arp -a`, `arp -d`, 추적 링크 줄을 뺐지만 계획(epic-1)대로 넣었다.

- 계획은 "ping 4회"만 적었다. 횟수 옵션을 1~10으로 막았다.

## 7. 남은 일과 다음 Task에 전할 것

- **T1.7.2(PR #33)가 먼저 병합되어야 한다.** 이 브랜치는 #33 위에 main을 합친 것이다. #33이 바뀌면 다시 맞춘다.
- T1.7.3(Switch 모델): `runtime.ts`의 `runModels()`에서 Switch에 `MissingModel` 대신 진짜 모델을 넣으면 `PING_DEVICE_UNSUPPORTED`가 사라진다. Runtime은 지금 PC 모델만 들고 있으므로 Switch 모델의 보관(MAC 테이블)도 같은 자리에 둔다. 회차를 시작할 때 할 일이 있으면 `start`에서 부른다.
- E4(Router): 위와 같다. Router는 `ArpModule`을 포트마다 쓴다.
- T1.10.1: 결과 분류는 `roundOf()`가 Trace를 읽어서 한다. `primaryDropSeq` 규칙을 바꾸면 여기와 맞춘다.
- T1.9.4: 콘솔 결과의 `{ kind: "trace", traceId }` 줄은 회차 줄 바로 뒤에 온다. Linux에서 보내지 못한 경우는 한 줄 뒤에 하나.
- `MissingModel` 때문에 오류가 난 실행도 kernel의 추적 번호를 하나 쓴다. 다음 ping의 추적 번호가 하나 건너뛴다.
- `ipconfig`, `ip addr`의 MAC은 아직 `macAddressFor(pc.id, 0)`이다. 값은 `portMac`과 같다. 이번에는 고치지 않았다.
