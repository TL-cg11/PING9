## 1. 목표와 완료 기준

- [x] 같은 목적지에 Static과 RIP 경로가 함께 있으면 Static이 테이블에 들어간다
- [x] Static을 지우면 RIP 경로가 올라온다
- [x] floating static: `ip route ... <AD>`로 AD를 RIP(120)보다 크게 주면 RIP가 이긴다. RIP가 없으면 그 Static이 쓰인다
- [x] `show ip route`에서 AD와 metric이 보인다
- [x] 공통 완료 조건: lint, 타입 검사, 단위 테스트, 빌드 (4절). 리뷰는 PR에서

RIP 경로를 실제로 배우는 일은 T11.2.2다. 이 Task에서는 테스트가 `routingTable`의 세 번째 인자로 RIP 경로를 직접 넣어 확인했다.

## 2. 진행 방식

1. 설계안(팀 합의 전)의 결정 7가지를 사용자와 정했다. 모두 실제 IOS와 같게 했다. 다만 `no ip route ... <AD>`에서 AD가 틀리면 지우지 않는다.
2. PR #41(T11.2.1)과 겹치는 파일(`codes.ts`, `errors.ts`, `running-config.ts`, `router-config.ts`)이 있어 PR #41 브랜치에서 시작했다.
3. 데이터: `StaticRoute.distance?`, `RouteEntryView`에 `"rip"`, `distance`, `metric`.
4. 경로 고르기(`routingTable`): 후보(Connected + Static + 배운 경로)에서 AD 255를 버리고, 목적지마다 AD가 가장 작은 경로만 남긴다. 테이블은 매번 계산하므로 Static을 지우면 RIP가 저절로 다시 올라온다.
5. `lookupRoute`: 가장 긴 접두사. 같은 길이면 AD → metric → 다음 홉 IP → 포트 이름. 지금까지의 "직접 연결 우선"은 AD 비교가 대신한다.
6. CLI: AD를 받는 `ip route`, `no ip route` 정의를 더했다. `show ip route`에 `AD/Metric` 칸, `show running-config`에 1이 아닌 AD.

### 주요 결정

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| AD 기본값: Connected 0, Static 1, RIP 120 (`DEFAULT_DISTANCE`) | 실제 IOS와 같다 | |
| Connected와 같은 목적지의 Static은 테이블에서 뺀다 | 실제 IOS와 같다. 패킷이 나가는 길은 지금과 같다 | 둘 다 보임 (지금까지) |
| AD 255는 테이블에 넣지 않는다 | 실제 IOS와 같다 | 넣음 |
| 같은 경로를 다른 AD로 다시 넣으면 AD만 바뀐다 | 실제 IOS와 같다 | 새 경로로 더함 |
| `no ip route ... <AD>`: AD가 틀리면 `ROUTE_NOT_FOUND`. AD를 빼면 AD와 상관없이 지운다 | 사용자 결정 | AD를 무시하고 지움 |
| AD 1은 저장하지 않는다 | `distance`가 없는 옛 문서와 같은 모양이 된다. `schemaVersion`을 올리지 않는다 | 늘 저장 |
| `show ip route`는 지금 표 형식에 `AD/Metric` 칸을 더함 | 실제 IOS의 `[120/2]`와 같은 값. 표 모양을 IOS 형식으로 바꾸는 것은 ssunyoung2와 따로 정한다 | IOS 형식으로 바꿈 |
| AD 숫자 읽기는 CLI, 1~255 범위는 reducer | 화면이나 직접 dispatch도 같은 규칙을 거친다 (AD-3) | CLI에서 범위까지 |
