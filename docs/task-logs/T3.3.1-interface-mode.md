## 2. 진행 방식

`interface-commands.test.ts`를 먼저 쓰고(모듈이 없어 실패) 구현했다.

1. **포트 이름 해석** (`port-name.ts`): 글을 종류(글자)와 번호로 나누고, 그 장비 종류의 포트 가운데 종류가 그 글자로 시작하고 번호가 같은 것을 찾는다. 하나면 그 포트다.
2. **글을 직접 읽는 매개변수** (`customParam`): 매개변수가 자기 읽는 함수를 가질 수 있게 했다. 읽는 함수는 장비 종류를 받는다.
3. **`interface` 명령 정의 둘**: 붙여 쓴 이름(`interface fa0/1`)과 띄어 쓴 이름(`interface fastethernet 0/1`).
4. **세션**: 인터페이스 세션이 이 장비에 없는 포트를 가리키면 config 모드로 돌아간다. config 모드로 물러난 세션을 저장한다.

### 주요 결정

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| 매개변수 종류(`ParamType`)를 늘리지 않고 `customParam`을 둠 | 인터페이스 이름은 장비 종류에 따라 답이 달라 종류 이름만으로 읽을 수 없다. 또 열려 있는 PR #9(T1.6.1)가 `ParamType`과 `readParam`의 같은 줄을 고치고 있어, 그 줄을 건드리지 않아야 충돌이 없다 | `ParamType`에 `interface`를 더하고 `readParam`에 장비 종류를 넘김 |
| 포트 이름 해석을 `cli/ios`에 둠 (`shared`가 아님) | 화면은 쓰지 않는다. `shared`를 바꾸지 않아도 된다 | `shared/port-name.ts`의 `shortPortName` 옆 |
| 띄어 쓴 이름은 정의를 따로 둠 | 해석기는 단어 하나에 토큰 하나다. 두 단어를 합치는 예외를 해석기에 넣지 않았다 | 해석기가 줄을 나누기 전에 `fastethernet 0/1`을 붙임 |
| 띄어 쓴 이름이 없는 포트면 오류에 위치가 없음 | 두 단어를 합쳐야 포트가 정해져서 실행 단계에서야 안다 | — |
| `interface` 정의에 장비 제한을 두지 않음 | Router 담당이 `INTERFACE_COMMANDS`를 자기 목록에 그대로 넣으면 된다 | Switch 전용 |

## 7. 남은 일과 다음 Task에 전할 것

- **Router 담당에게**: `INTERFACE_COMMANDS`를 Router의 정의 목록에 넣으면 `interface g0/0`이 동작한다. 장비 종류에 따라 달라지는 값이나 한 명령어만 쓰는 형식은 `customParam(이름, 설명, 읽는 함수)`로 만든다.
- **띄어 쓴 이름의 도움말이 해석과 어긋난다 (검토에서 나옴, 고치지 않음)**: `interface fa 0/9 ?`는 `<cr>`을 보이지만 Enter를 치면 없는 포트라 `CLI_INVALID_VALUE`가 난다. 두 단어를 합쳐야 포트가 정해지는데 해석기는 단어를 하나씩 본다. 붙여 쓴 이름(`fa0/9`)은 해석 단계에서 걸러져 어긋나지 않는다.
- `interface range`는 넣지 않았다 (설계 14절 6번).
- T3.3.2가 이 모드에 `shutdown`을 넣는다.
