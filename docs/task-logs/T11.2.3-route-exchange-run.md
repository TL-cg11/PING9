## 2. 진행 방식

1. 설계안(팀 합의 전)의 결정 7가지를 사용자가 모두 추천대로 정했다. T11.2.2와 커밋·PR을 하나로 하기로 해서 같은 브랜치에서 이어 했다 (기록 문서는 따로, PR #38 선례).
2. `routing-inputs.ts`: RIP 결과를 바꿀 수 있는 값(Router·Switch 설정, 링크, 장비 목록)을 만들고, `dispatch` 앞뒤로 비교한다.
3. `Simulator`: `dispatch` 뒤 그 값이 바뀌었고 앞뒤 어디에든 RIP Router가 있으면 교환 1회. `load` 뒤 RIP Router가 있으면 교환 1회.
4. `Runtime.exchangeRoutes`: Trace를 목록에 넣고, 앞의 RIP Trace를 뺀다. 요약에 참여 Router 수와 배운 경로 수.
5. `TraceSummary`를 `kind`로 나뉘는 union으로. 웹에서 `targetIp`를 읽는 두 곳(`app.tsx`, 테스트 하나)을 `kind`로 좁혔다.
6. `clear ip route *` (Router, privileged): `RuntimeAccess.exchangeRoutes`로 교환 1회.
7. T11.2.2의 테스트 두 개를 고쳤다. 문서를 열거나 RIP 구성을 바꾸면 이제 교환이 저절로 돌기 때문이다.

### 주요 결정

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| Router·Switch 설정, 링크, 장비 목록이 바뀌었을 때만 교환 | RIP 결과는 이것으로만 정해진다. 장비를 끌어서 옮기는 동안 `device/move`가 수십 번 와도 교환이 돌지 않는다. 바뀐 값을 비교하므로 새 Command가 생겨도 고칠 곳이 없다 | 모든 dispatch마다 / Command 종류 목록으로 고르기 |
| 문서를 열 때 교환 1회 | 배운 경로는 저장하지 않는다(AD-4). 안 하면 저장한 RIP 실습을 열었을 때 ping이 안 된다 | 안 함 |
| `TraceSummary`는 union | ping의 출발 장비·목적지가 경로 교환에는 없다. 컴파일러가 `kind` 확인을 강제한다 | 칸을 선택으로 |
| 목록에 RIP Trace는 가장 최근 하나 | 설정을 한 줄 칠 때마다 교환이 돈다. 다 남기면 ping 기록(최대 20개)이 밀려난다 | 다 남김 / 따로 목록 |
| 한도에 걸리면 그때까지 배운 경로를 쓰고 `loop-guard` | ping과 같은 규칙(FR-30) | 모두 버림 |
| `clear ip route *` | 실제 명령이다. 설정을 바꾸지 않고 다시 배우기를 볼 수 있다 | 안 넣음 |
