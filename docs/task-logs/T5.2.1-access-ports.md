## 2. 진행 방식

테스트를 먼저 쓰고 실패를 확인한 뒤 구현하는 순서로 네 부분을 했다.

1. **`shared`**: 폐기 사유 `VLAN_INACTIVE { device, port, vlan }`.
2. **reducer** (`switch-port.ts`): `switchport/set-mode`, `switchport/set-access-vlan`.
3. **명령어** (`switchport-commands.ts`): 인터페이스 설정 모드의 네 가지.
4. **전달 규칙**: T1.7.3이 비워 둔 두 자리(`classify`, `egress`)에 access 포트의 규칙을 넣었다.
5. **화면**: 속성 패널의 포트 줄에 `VLAN n` 또는 `trunk` 표시, 캔버스의 링크에 `VLAN n` 표시, VLAN 번호별 색.

### 주요 결정

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| `VLAN_INACTIVE`를 `VLAN_BLOCKED`와 따로 둠 | `VLAN_BLOCKED`의 params는 "프레임의 VLAN과 포트의 VLAN이 다름"이다. "VLAN이 지워짐"에 쓰면 사유 문장이 틀린다 (설계 5.1절) | `VLAN_BLOCKED` 재사용 |
| 모드를 바꿔도 access VLAN과 허용 목록은 그대로 | 실제 장비와 같다. access로 돌아오면 전의 VLAN이 다시 쓰인다 | 모드를 바꾸면 초기화 |
| trunk 모드인 포트에도 access VLAN을 저장 | 위와 같은 이유 | 거부 |
| 자동으로 만들면 한도(64개)를 넘는 경우는 거부 | 넘기면 `validateDocument`를 통과하지 못하는 문서가 된다 | VLAN 없이 포트만 바꿈 |
| 모드가 `access`·`trunk`가 아니면 `DOCUMENT_INVALID_SHAPE { path: "mode" }` | 이 경우에 맞는 오류 코드가 없다. CLI는 키워드가 둘뿐이라 여기까지 오지 않는다 | 새 오류 코드 |
| 캔버스의 링크에는 VLAN 1을 표시하지 않음 | 시안은 VLAN 10·20만 표시한다. VLAN을 쓰지 않는 문서의 모든 링크에 `VLAN 1`이 붙으면 어지럽다 | 모든 access 링크에 표시 |
| 시안에 없는 번호의 색은 네 가지 가운데 번호로 고름 (`vlan-color.ts`) | 설계 8.2절: "번호에 따라 정해진 색 목록에서 고른다". 같은 번호는 항상 같은 색이다 | 전부 회색 (T5.4.1의 임시 처리) |
| 이 Task에서 trunk 포트는 모든 VLAN을 태그 없이 나르는 것으로 둠 | trunk의 태그와 허용 목록은 T5.3.1이다 | 한 번에 넣음 |

## 6. 계획과 달라진 점

- **`shared`에 폐기 사유 `VLAN_INACTIVE`를 더했다.** 02 문서 FR-47의 표에 없는 사유다. `codes.test.ts`의 "FR-47의 표와 같다" 테스트를 "FR-47의 표에 `VLAN_INACTIVE`를 더한 것"으로 고쳤다. 계획 문서 본문은 팀이 합의한 뒤에 고친다.
- **폐기 사유의 한국어 문구는 넣지 않았다** (T1.9.1의 몫, 설계 8.4절).
- **통합 테스트 "다른 VLAN으로 ping"은 하지 않았다.** `switchForward`의 단위 테스트로 규칙을 확인했다.

## 7. 남은 일과 다음 Task에 전할 것

- **kernel 담당에게**: `switchForward`의 `blocked`가 "다른 VLAN으로의 ping이 왜 실패했는가"의 재료다. 이것을 Trace의 폐기 이벤트로 적고 실패 원인으로 고르는 일은 T5.2.2와 T1.10.1이다.
