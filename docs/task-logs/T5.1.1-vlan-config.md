## 2. 진행 방식

테스트를 먼저 쓰고 실패를 확인한 뒤 구현하는 순서로 세 단계에 걸쳐 했다.

1. **`shared`**: 오류 코드 2개, Switch 구성 읽기 함수, 포트 이름 줄임 함수, 시안과 같은 예시 문서.
2. **reducer**: `vlan/create`, `vlan/rename`, `vlan/remove` 처리기와 구성 정규화.
3. **CLI**: `vlan`, `no vlan`, `name`, `show vlan brief`.

### 주요 결정

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| Switch 구성 읽기 함수를 `shared`에 둠 (`switchPort`, `switchPorts`, `switchVlans`, `vlanAccessPorts`) | "`ports`에 없는 포트는 켜짐·access·VLAN 1"이라는 기본값 규칙과 VLAN 소속을 engine과 화면이 각자 계산하면 어긋난다. 화면은 engine에서 `Simulator`만 가져올 수 있으므로(AD-16) 자리는 `shared`다 | `SwitchView`에 필드를 더함 (`view.ts`가 "구성 값은 Document에 있으므로 다시 담지 않는다"고 정해 둠) |
| VLAN 1은 구성에 없어도 있는 것으로 침 | `validateDocument`는 `vlans: []`인 문서도 통과시킨다. 검증 규칙을 바꾸지 않고 읽는 쪽에서 채운다 | `validateDocument`가 VLAN 1을 요구하게 함 (`shared`의 검증 변경) |
| VLAN 1은 지울 수도, 이름을 바꿀 수도 없음 (`DEFAULT_VLAN_READONLY`) | 실제 장비와 같다. 계획은 삭제 불가만 적었다 | 이름 변경은 허용 |
| VLAN을 지워도 그 VLAN을 쓰던 포트의 `accessVlan`은 그대로 | 계획(T5.2.1): "포트의 VLAN이 지워지면 그 포트는 통신 불가". 실제 장비와 같다 | 포트를 VLAN 1로 되돌림 |
| 정규화가 VLAN 1을 넣으면 한도(64개)를 넘는 경우에는 넣지 않음 | VLAN 1 없이 64개가 든 문서를 가져와 고치면 65개가 되어 `validateDocument`를 통과하지 못했다 (검토에서 발견). 읽는 쪽은 여전히 VLAN 1이 있는 것으로 친다 | 그런 문서의 변경을 거부 |
| 경계 밖에서 온 값을 글로 바꿀 때 `String()`을 쓰지 않음 (`describe.ts`의 `describeValue`) | `{ toString: 1 }` 같은 값에서 `String()`이 예외를 던졌다 (검토에서 발견). engine은 어떤 입력에도 예외를 던지지 않아야 한다 (AD-16) | `try`/`catch` |
| reducer가 Switch 구성을 정규화해서 돌려줌 | 같은 구성이 항상 같은 Document가 되어야 `show running-config` 왕복(T3.4.1)을 비교할 수 있다 | 정규화 없이 비교할 때만 맞춤 |
| 이름 없이 만든 VLAN의 이름은 `VLAN0010` 형태 | 실제 장비와 같고 `checkVlanName`을 통과한다 | 빈 이름 |
| `vlan <번호>`는 이미 있는 VLAN이면 Command를 내지 않고 모드만 바꿈 | `docVersion`이 쓸데없이 오르지 않는다. reducer의 `vlan/create`는 중복을 `DUPLICATE_VLAN`으로 거부한다 | reducer가 중복 생성을 조용히 받아들임 |
| `show vlan brief`의 Ports 열에는 access 포트만, 한 줄에 3개씩 | trunk 포트는 한 VLAN에 속하지 않는다. 3개씩은 터미널 창의 너비에 맞춘 것이다 | 80자에서 줄바꿈 |

## 6. 계획과 달라진 점

- **`shared`에 오류 코드 2개와 구성 읽기 함수를 더했다.** 계약의 변경이므로 PR에서 두 팀원 모두 확인해야 한다. 기존 코드와 타입은 바꾸지 않았고 더하기만 했다.
- **E3이 끝나기 전에 T5.1.1을 했다.** 계획의 선행은 T3.4.1(`show running-config`)이다. 화면에서 일찍 확인하려고 모드(T3.1.1, T3.1.2) 바로 뒤에 했다.
- **직렬화(`serialize`)와 왕복 테스트를 넣지 않았다.** T3.4.1에서 그때까지의 모든 명령 정의에 함께 넣는다.
- **VLAN 1의 이름 변경도 막았다.** 계획은 삭제 불가만 적었다.
- **VLAN 1이 없는 문서도 받아들인다.** 읽는 쪽에서 VLAN 1을 채운다. `validateDocument`는 바꾸지 않았다.

## 7. 남은 일과 다음 Task에 전할 것

- **`device/add` 처리기를 만드는 사람에게**: Switch의 기본 구성은 `{ vlans: [{ id: 1, name: "default" }], ports: {} }`다. 이것이 정규화된 형태다.
- **Switch 구성을 읽는 모든 코드에게**: `config.ports[port]`나 `config.vlans`를 직접 읽지 말고 `switchPort`, `switchPorts`, `switchVlans`, `vlanAccessPorts`를 쓴다. 기본값과 VLAN 1이 채워져서 나온다.
- **처리기를 더하는 사람에게**: 처리기는 `packages/engine/src/handlers/`의 자기 파일에 두고 `reducer.ts`의 `handlers`에 한 줄만 더한다. `simulator.test.ts`의 `HANDLED_TYPES`에도 자기 Command의 type을 더한다.
- T5.2.1(`switchport access vlan`)은 `handlers/switch-common.ts`의 `findSwitch`와 `withSwitchConfig`를 그대로 쓴다. 없는 VLAN의 자동 생성과 알림 `VLAN_AUTO_CREATED`도 그 Task에서 넣는다.
- T3.4.1에서 넣을 직렬화: VLAN 1은 출력하지 않고, 이름이 `defaultVlanName(번호)`와 같으면 `name` 줄을 생략한다.
