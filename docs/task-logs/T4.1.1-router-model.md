## 2. 진행 방식

기존 Router 타입과 포트 이름, 상태 계산은 재사용했다. 생성 명령 처리기와 CLI 장비별 등록 목록이 비어 있어서 Router 생성/기본 조작에 필요한 부분을 추가했다. Router를 추가한 뒤 설정을 바꾸는 과정은 기존 Simulator 공개 API를 그대로 따른다.

```text
화면의 Router 버튼
→ simulator.dispatch(device/add)
→ reducer가 기본 구성과 이름을 생성하고 문서를 검증
→ Snapshot 갱신
→ 캔버스/속성 패널에서 R1과 포트 상태 표시

R1 콘솔의 no shutdown
→ 공통 CLI 정의
→ simulator.dispatch(interface/set-admin)
→ Router 구성 갱신
→ show와 화면이 같은 computeViews 결과 표시
```

### 주요 결정

| 결정 | 이유 | 선택하지 않은 대안 |
|---|---|---|
| `device/add`를 종류 공통 처리기로 구현 | Router만 생성하는 별도 경로를 만들지 않고 같은 계약을 재사용 | Router 전용 생성 Command 추가 |
| Router는 인터페이스 4개에 `adminUp: false`를 명시 | T4.1.1의 기본 구성과 켜기/끄기 검증을 직접 표현 | 기본값 해석에만 의존 |
| 이름은 기존 모든 장비 이름을 확인해 `R1`, `R2` 순으로 선택 | 다른 종류의 장비도 R1이라는 이름을 가질 수 있음 | Router 수에 1을 더해 이름 생성 |
| 공통 CLI 해석기와 기본/인터페이스 정의 재사용 | 모드, 줄임 입력, Tab과 도움말이 Switch와 같은 규칙으로 동작 | Router 전용 파서 구현 |
| 화면에서는 버튼 클릭으로 추가 | 현재 읽기 전용 캔버스에서도 Router를 생성하고 조작 가능 | 전체 드래그 편집기까지 이 Task에서 구현 |
| 공통 문서 검증기의 반환값 사용 | 위치/문서 크기/참조 규칙을 재정의하지 않고 호출자의 위치 객체도 공유하지 않음 | 별도의 전체 문서 검증 코드 추가 |

## 6. 계획과 달라진 점

- **T4.1.1은 부분 구현이다.** T1.7.2의 DeviceModel/링크 연결, T1.8.1의 ARP, T1.8.2의 IPv4/ICMP 모듈이 없어 패킷 처리 모델은 조립하지 않았다. 이 Task만으로 ping을 지원하지 않는다.
- **T1.3.1의 `device/add` 부분을 먼저 구현했다.** Router 생성에 공통 경로가 필요했고 아직 처리기가 없었다. PC/Switch도 같은 처리기로 생성할 수 있지만 이동·이름 변경·삭제는 구현하지 않았다. T1.3.1을 완료로 표시하지 않는다.
- **T1.3.2의 드래그 배치를 기다리는 대신 클릭 배치를 제공한다.** 추가 위치는 웹이 기존 장비와 겹치지 않는 격자에서 정한다. 전체 캔버스 편집·링크 연결은 이 작업에 포함하지 않는다.
- **T4.1.3의 `show ip interface brief` 조회를 먼저 추가했다.** 포트 기본 상태와 켜기/끄기를 콘솔에서도 확인하기 위해서다. 직접 연결 경로와 `show ip route`는 아직 구현하지 않았다.
- 공통 CLI의 `hostname`은 기존 Switch와 마찬가지로 `device/rename` 처리기 구현을 기다린다. Router 전용 예외로 문서를 직접 바꾸지 않는다.
