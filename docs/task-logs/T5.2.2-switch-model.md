## 2. 진행 방식

1. 테스트를 먼저 썼다. `switch-model.test.ts`는 진짜 kernel 위에서 가짜 PC(받은 것만 적는 `FakePc`)와 Switch 모델만 돌려 이벤트 순서, 부모 관계, 도착 시각, 태그를 확인한다. `switch-ping.test.ts`는 공개 인터페이스(`createSimulator`)로만 ping·`show mac address-table`·스냅샷을 확인한다. 둘 다 처음에는 모듈이 없어 실패했다.
2. `SwitchModel`을 PC 모델(T1.8.3)과 같은 방식으로 만들었다. 구성은 복사하지 않고 매번 `getDocument()`로 읽고, 들고 있는 것은 MAC 주소 테이블뿐이다. 포트 상태는 화면과 같은 계산(`computeViews`)으로 읽는다 (AD-7).
3. Runtime에 Switch 모델의 보관(`switches`)을 PC와 나란히 두고, `runModels()`에서 Switch에 `MissingModel` 대신 진짜 모델을 넣었다. Router만 `MissingModel`로 남는다.
4. `RuntimeAccess`에 `macTable(deviceId)`를 더하고 `show mac address-table`이 그것을 읽게 했다. 화면의 테이블은 `fillViews`가 채운다.
5. 테스트의 틀린 기대 다섯 개를 고쳤다 (앞 회차의 도착 수를 빼먹음, 만료 시각을 도착 시각 기준으로 안 셈, 링크 셋을 넷으로 셈, 다른 서브넷으로 ping해 PC에서 `NO_GATEWAY`로 먼저 멈춤, `DeviceView` 타입 좁히기). 구현은 처음 그대로 통과했다.
6. 기존 테스트 하나를 바꿨다: `ping.test.ts`의 "모델이 아직 없는 장비"는 Switch 대신 Router를 지나는 문서로 확인한다.
7. 화면에서 확인하고(4절), 읽기 전용 검토 에이전트(Claude)의 검토를 받았다. 고친 것:
   - 아직 모델이 없는 Router 앞에 Switch가 있으면, `PING_DEVICE_UNSUPPORTED`로 멈춘 ping 중에 Switch가 배운 주소가 남고 스냅샷은 그대로여서 화면(빈 테이블)과 `show mac address-table`(한 줄)이 어긋났다. 회차마다 Switch 테이블의 `checkpoint()`를 받아 두고 멈추면 되돌린다. 테스트 추가.
   - 프레임마다 문서 전체의 포트 상태(`computeViews`)를 계산했다. 큰 문서에서 Switch 고리가 생기면 LOOP_GUARD까지 2,000프레임 × 전체 계산이라 느리다. 그 장비의 포트만 계산하는 `portViewsOf`를 `views.ts`에 두고 화면과 모델이 같이 쓴다 (AD-7의 한 곳).
   - `configChanged`의 Switch 가지(반환값)를 확인하는 테스트가 없었다. 관계없는 변경(이동)에는 `runtimeVersion`이 그대로, VLAN 변경과 Switch 삭제에는 오르는 테스트 추가.
   - `vlan ?? 0`처럼 불변식을 가리는 코드, flooding 테스트의 약한 기대, 오래된 주석(`views.ts`, `forwarding.ts`, `ping.test.ts`).

### 주요 결정

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| 들어오다 폐기(`IF_DOWN`, trunk 허용 안 됨, access 포트에 다른 태그, 지워진 VLAN)는 `FRAME_RECEIVED` 없이 폐기 이벤트 하나만 남긴다 | 꺼진 포트는 받은 것이 아니다. 폐기 이벤트에 `inPort`가 있어 어디로 들어왔는지는 보인다 | 받음 + 폐기 두 개 (같은 시각의 재생 단계가 둘이 됨) |
| flooding에서 VLAN 때문에 빠진 포트(`blocked`)는 **어디로도 나가지 못했을 때만** 폐기 이벤트로 적는다 | kernel은 `NOT_FOR_ME`가 아닌 첫 폐기를 실패 원인(`primaryDropSeq`)으로 잡는다. 다른 포트로 잘 나간 프레임의 "빠진 포트"가 원인으로 잡히면 틀린 설명이 된다. 반대로 갈 곳이 하나도 없을 때는 그것이 바로 원인이다 (한 Switch 안의 다른 VLAN → `VLAN_BLOCKED`) | 항상 적기 (설계 9절 18번의 "`blocked`를 폐기 이벤트로"는 이렇게 읽을 수 있었다), 전혀 안 적기 (한 Switch 안의 VLAN 분리 실패에 원인이 없어짐) |
| 목적지가 받은 포트 쪽에 있으면(`samePort`) 받음(과 학습)만 적고 폐기로 적지 않는다 | 정상 동작이다. 폐기로 적으면 실패 원인으로 잡힌다 | `NOT_FOR_ME`류의 폐기 |
| 전달 이벤트의 `frame`은 나가는 모양(태그를 붙이거나 뗀 것)이고 `parentSeq`는 학습 이벤트(없으면 받음 이벤트)다 | 재생에서 trunk 구간의 프레임에 태그가 보인다 (FR-33). 받음 → 학습 → 전달의 사슬 | 받은 모양 그대로 |
| Switch는 kernel 타이머를 쓰지 않는다. 만료는 프레임을 받을 때(`switchForward`)와 화면용 목록(`macTableView`)에서 시각으로 판단한다 | 실행 밖에서도 `view()`가 불리므로 모델이 `now` 함수를 받는다. Runtime이 `kernel.now`를 넘긴다 | 300초 타이머 |
| 포트 상태는 `computeViews`로 읽는다 | 상대 포트가 꺼진 `peer-down`도 `up`이 아니라서 그 포트로 내보내지 않는다. 화면과 같은 규칙 (AD-7) | `isAdminUp`만 보기 |
| 설계의 18번에 있던 "실패 사유 문구"는 넣지 않았다 | web은 아직 추적을 그리지 않는다 (T1.9.4, T1.10.2). 문구 카탈로그가 생길 때 폐기·이벤트 코드 전부를 한 번에 넣는 것이 맞다 | 쓰이지 않는 문구 파일 |

새 테스트가 확인하는 것:

- PC 2대 + Switch 1대: 브로드캐스트는 받음 → 학습 → 켜진 다른 포트로만 flooding (링크 없는 Fa0/3~8은 폐기로 적지 않음), 1,000µs씩 늦게 도착, 부모 사슬, `validateTrace` 통과. 배운 목적지는 `FRAME_FORWARDED` 하나. 모르는 유니캐스트는 `broadcast: false`. 같은 포트의 목적지는 받음만. 같은 포트에서 다시 보면 학습을 다시 적지 않음. 꺼진 포트는 `IF_DOWN`만, `primaryDropSeq`. `view()`와 300초 만료(도착 시각 기준). `onConfigChanged`가 VLAN이 바뀐 포트의 항목을 지우고, 이름 변경에는 그대로.
- VLAN 예시 문서(SW1 trunk 10·20, SW2 trunk 20): VLAN 10 브로드캐스트가 trunk에 태그 10으로 나가고 SW2에서 `TRUNK_NOT_ALLOWED`로 끝남 (`primaryDropSeq`, PC3에 닿지 않음). VLAN 20은 trunk를 건너 PC4에만 태그 없이 3,000µs에 도착, frameId 하나, SW2가 Fa0/8에서 PC2를 배움. trunk를 빼면 한 Switch 안의 다른 VLAN으로는 `VLAN_BLOCKED` 폐기(원인). 다른 포트로 나갔으면 빠진 포트를 폐기로 적지 않음. SW2가 10을 허용하면 건너감.
- 공개 인터페이스: PC1 → PC2 ping 성공과 Switch 이벤트, 스냅샷과 `show mac address-table`의 테이블, `runtimeVersion` 증가와 `load` 뒤 비움, access VLAN을 바꾸면 그 포트의 항목만 사라지고 `runtimeVersion`이 오름(이동에는 그대로), Switch를 지우면 오르고 같은 ID로 다시 만들어도 빈 테이블, Router 앞의 Switch는 멈춘 ping에서 배운 것을 되돌림(스냅샷 그대로, `show mac address-table` 비어 있음). VLAN 문서에서 PC2 → PC4 성공, PC1 → PC3 실패(`TRUNK_NOT_ALLOWED`가 원인, `Destination host unreachable`), 같은 서브넷·다른 VLAN의 PC1 → PC2 실패(`VLAN_BLOCKED`가 원인), `switchport trunk allowed vlan add 10` 뒤 PC1 → PC3 성공.

## 6. 계획과 달라진 점

- **Task ID의 뜻이 계획과 다르다.** 04-tasks의 T5.2.2는 "폐기 사유와 문구"(`VLAN_BLOCKED` 사유, VLAN 자동 생성 알림, 실패 사유 문구)다. 그중 `VLAN_BLOCKED` 사유는 T5.2.1에서, VLAN 자동 생성 알림(`VLAN_AUTO_CREATED`)도 T5.2.1에서 이미 넣었다. 설계 문서 9절은 남은 "kernel 연결"을 18번으로 두고 T5.2.2의 기록에 적기로 했으므로, 이 문서가 그것이다. 실패 사유 **문구**는 web이 추적을 그리기 시작할 때(T1.10.2) 코드 전부와 함께 넣는다.
- 설계 9절 18번의 "`blocked`를 폐기 이벤트로"는 "어디로도 나가지 못했을 때만"으로 좁혔다 (2절의 결정).
- T1.8.3 기록의 "회차를 시작할 때 할 일이 있으면 `start`에서 부른다"는 Switch에는 필요 없었다. 회차 사이에 비울 상태가 없다.

## 7. 남은 일과 다음 Task에 전할 것

- **T1.10.1 (실패 원인 판정)**: Switch의 폐기 이벤트는 들어오다 폐기(`inPort`만)와 나가지 못한 폐기(`inPort`와 `outPort`) 두 가지다. `blocked`를 적는 조건(위)을 바꾸면 `switch-ping.test.ts`의 `VLAN_BLOCKED` 테스트와 맞춘다. 검토에서 나온 한계: 목적지 PC가 VLAN이 다른 포트 뒤에 있는데 같은 VLAN의 다른 포트로는 flooding이 나간 경우, 원인은 `ARP_TIMEOUT`으로 잡히고 VLAN이 달랐다는 사실은 추적에 남지 않는다. 폐기가 아닌 "참고" 이벤트나 kernel에 "원인이 아닌 폐기" 표시가 있어야 담을 수 있다.
- **T1.9.x, T1.10.2 (추적 재생과 문구)**: 이벤트 코드별 한국어 문구가 아직 없다. `FRAME_FLOODED`는 포트마다 하나라 재생에서는 같은 시각의 묶음으로 보여야 한다. trunk 구간의 전달 이벤트와 도착 프레임에는 `vlanTag`가 있다.
- **E4 (Router 모델)**: `runtime.ts`의 `runModels()`에서 `router` 가지만 바꾸면 된다. `MissingModel`과 `PING_DEVICE_UNSUPPORTED`는 그때 지운다. `ping.test.ts`의 "모델이 아직 없는 장비" 테스트도 그때 지운다.
- `show mac address-table`은 Runtime 없이 만든 콘솔(일부 테스트)에서는 빈 테이블이다.
- MAC 항목의 만료(300초 가상 시간)는 ping 몇 번으로는 일어나지 않는다. 화면에서 확인하려면 kernel 시각이 그만큼 흘러야 한다.
- Switch가 문서에서 지워졌다가 같은 ID로 다시 만들어지면 테이블은 비어 있다 (`configChanged`가 모델을 버린다).
