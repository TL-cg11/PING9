## 1. 무엇을 만들 것인가

**외부 PC가 VPN에 접속하면 내부망 PC와 통신하고, 연결을 끊으면 그 접근이 사라지는 실습**을 만든다.

기존 GRE·IPsec 실습은 두 라우터 사이에 터널을 설정했다. 이번에는 PC가 VPN 클라이언트이고 Router가 접속을 받는 게이트웨이다. 새 장비 종류를 만들기보다 기존 PC·Router를 확장한다. Firewall은 별도 장비로 그대로 유지한다.

```text
외부 PC_A ── ISP ── FW1 ── R1 (VPN 게이트웨이) ── 내부 PC_B
    └──────── 교육용 TLS 기반 가상 터널 ────────┘
```

최종 사용 흐름:

1. R1에 접속 포트, 서버 식별자, 신뢰/인증 정책, 가상 IP 풀, 허용 내부 대역을 설정한다.
2. PC_A에서 서버 주소와 공개 실습용 인증 정보를 설정하고 연결한다.
3. 접속 과정이 성공하면 가상 IP를 할당받는다.
4. PC_A가 허용된 내부 IP로 ping을 보내면 가상 터널을 통해 전달된다.
5. 접속 상태·안쪽/바깥쪽 주소·카운터·거절 이유를 확인한다.
6. 연결 해제·실패·만료 때 가상 IP와 세션 경로를 회수한다.

## 2. 구현 수준: 제안과 실제 기능을 구분

**추천 기본안은 기존 IPsec과 같은 교육용 시뮬레이션**이다. 사용자가 SSL VPN의 실제 암호화 수준을 새로 지정한 것은 아니므로, 아래는 구현 시 적용할 기본 제안이다. 실제 TLS가 필요하다는 요구가 생기면 착수 전에 별도 범위로 변경한다.

| 항목 | 이번 기본 제안 | 이번 범위 밖 |
|---|---|---|
| 접속 방식 | 원격 PC → Router, 세션을 맺는 터널 방식 | 웹 포털, 브라우저 앱 프록시 |
| 프로토콜 표현 | TLS 기반 VPN의 접속·검증·데이터 흐름을 간소화해 재현 | 실제 TLS/OpenVPN wire protocol 호환 |
| 서버 신뢰 | 서버 ID·신뢰 CA ID·호스트 이름·가상 만료 시각 검사 | 실제 X.509 서명 검증·인증서 발급·개인키 |
| 사용자 인증 | 공개 실습용 사용자/인증 식별자와 허용 사용자 목록 검사 | 실제 계정·비밀번호·MFA·서비스 로그인 |
| 데이터 | 세션에 연결된 IPv4 ICMP를 감싸고 복원 | HTTP 웹 접속, 일반 TCP/UDP 앱 트래픽 |
| 라우팅 | 허용 대역만 터널로 보내는 split tunnel | full tunnel, NAT, 인터넷 출구 VPN |
| 동시 접속 | 서버 1개당 최대 4개 PC, PC당 활성 세션 1개 | 다중 게이트웨이·고가용성·로밍 |
| 암호화 | 없음. 모든 관련 UI/조회에 교육용임을 표시 | Web Crypto/Node crypto를 통한 실제 암호화 |

“SSL VPN”은 실습 기능 이름으로 쓰고, 화면에는 **TLS 기반 원격 접속 VPN · 교육용 시뮬레이션**을 병기한다. 실제 SSL 구버전이나 TLS 암호화가 동작한다고 표시하지 않는다. `connected`는 간소화된 검증이 끝났다는 뜻이지 실제 보안 연결의 증거가 아니다.

## 4. 구현 계약

### 4.1 저장 설정과 동적 상태

| 위치 | 보관 내용 |
|---|---|
| Document | 서버 활성 여부·listen 물리 IP/포트·내부 가상 IP·풀·허용 대역·서버/CA 식별자·허용 사용자·세션 수명, PC의 서버·신뢰 설정·공개 인증 식별자 |
| Runtime | 접속 상태·세션 ID·할당 IP·시작/만료 가상 시각·송수신 sequence/카운터·활성 세션 경로 |
| CLI candidate | VyOS 방식으로 편집하는 경우 미적용 서버 설정. commit 전 트래픽에 영향 없음 |

내보내기는 **설정만 저장**한다. 가져오기/새로고침은 disconnected 상태로 시작하고, 이전 연결을 복구한 것처럼 보이지 않게 한다. 저장된 가상 IP 할당·세션·연결 경로는 없어야 한다. 실제 비밀번호·인증서·개인키는 받지 않는다.

### 4.2 접속과 종료

```text
DISCONNECTED → CONNECTING → VALIDATING → CONNECTED
                   └──────── 실패 ───────→ FAILED
CONNECTED → 연결 해제 / 만료 / 관련 설정 변경 / 링크 장애 → DISCONNECTED
```

- connect는 Runtime이 커널 실행을 시작해 순서가 있는 제어 메시지들을 주고받는다. connect/disconnect에도 trace를 남긴다.
- 메시지마다 세션·클라이언트·서버·실습 식별자·송수신 방향을 확인한다. 중복 connect로 주소나 세션을 두 개 만들지 않는다.
- 신뢰 검사·인증·풀 확인을 모두 통과한 다음 가상 IP와 세션 경로를 한 번에 활성화한다.
- 접속 timeout·서버 비활성·잘못된 인증·풀 고갈에서는 주소를 남기지 않는다. 재시도는 명시적인 connect로 한다.
- 실제 TCP 재전송/혼잡 제어/바이트 스트림은 구현하지 않는다. 교육용 연결 제어 메시지와 timeout만 범위를 명시해 구현한다.
- 수명과 timeout은 커널 가상 시간으로만 판단한다. 백그라운드 실제 시간 타이머나 자동 재연결은 만들지 않는다.
- 다음 실행/조회 시에도 만료를 검사한다. 가상 시간이 진행되지 않았는데 벽시계 기준으로 만료시키지 않는다.
- 클라이언트 물리 IP·서버 설정·인증 정책의 변경은 관련 세션을 무효화한다. 장비 위치/이름 변경은 세션을 끊지 않는다.
- 이 첫 모델은 연결 중 물리 링크 장애를 감지하면 세션을 무효화한다. 복구 뒤 재접속한다. 실제 제품의 keepalive 동작과 동일하다고 주장하지 않는다.

### 4.3 주소·경로와 패킷 처리

- 풀은 IPv4 CIDR 하나, 서버 가상 IP는 그 안의 고정 주소 하나로 시작한다. 서버·네트워크·브로드캐스트 주소를 제외하고 작은 호스트 IP부터 결정적으로 할당한다.
- 풀은 기존 물리 LAN/WAN, 다른 터널 대역과 겹치지 않게 검증한다. 활성 클라이언트마다 유일한 IP를 할당하고 종료 시 반환한다.
- PC_A의 기존 물리 IP·기본 게이트웨이는 유지한다. 허용 대역에 속하는 패킷만 가상 IP를 출발지로 사용해 터널에 넣는다.
- 서버 endpoint까지의 바깥 경로는 항상 물리 경로를 사용해 터널 재귀를 막는다. VPN의 허용 대역 안에 endpoint가 포함되는 구성은 거절한다.
- 허용 대역에 대한 세션 전용 경로는 미접속·접속 실패·종료 시 제거한다. 다른 대역은 기존 일반 통신을 유지한다.
- VPN 프로필의 보호 대역은 미접속 시 일반 경로로 조용히 우회하지 않고 VPN 미접속 사유로 거절하는 교육 정책을 기본으로 한다. 프로필을 끄면 그 정책도 해제하며, 이는 실제 제품 공통 규칙이 아닌 PING9 기본안이다.
- 서버는 안쪽 출발 IP가 해당 세션에 할당한 IP인지, 목적지가 허용 대역인지 검사한다. 다른 클라이언트의 주소로 위장하거나 허용 대역 밖으로 나가면 폐기한다.
- 안쪽 ICMP는 가상 VPN 경계를 포함한 라우팅에서 TTL을 감소시키며 바깥 TTL과 분리한다. 기대 hop 수는 전송 경로별 테스트로 고정한다.
- 서버가 LAN으로 전달할 때는 기존 ARP/MAC/케이블 처리를 사용한다. 내부 PC의 응답은 기본 게이트웨이로 돌아오고, 서버가 목적지 가상 IP를 활성 세션에 대응시켜 다시 감싼다.
- 세션 ID·방향·sequence로 중복 데이터 및 종료된 세션 패킷을 거절한다. 이는 교육용 검사이며 실제 암호학적 변조 방지가 아니다.
- 기존 GRE/ESP 또는 다른 SSL VPN 안에 다시 감싸는 중첩은 이번에 지원하지 않는다. 이 제한을 실행 시 명확히 거절한다.

### 4.4 Firewall과 연결

- 바깥 TCP 목적지 포트를 선택한 서버 listen 포트와 일치시킨다. 실습에서는 443을 사용하되 설정 가능하게 한다.
- Firewall의 FORWARD가 바깥 요청·응답 모두를 검사해야 한다. 현재 Firewall은 **무상태**이므로 접속 요청을 허용했다고 역방향이 자동 허용되는 것은 아니다.
- `-p tcp --dport 443` 규칙과 역방향 `--sport 443` 규칙을 각각 검증한다. 차단되면 연결 상태만 성공으로 바꾸지 않는다.
- 방화벽을 우회하는 Runtime의 장비 ID 직통 전달을 하지 않는다. 제어·데이터 메시지 모두 실제 토폴로지 경로를 지난다.
- 내부망 필터링은 첫 단계에서 서버의 허용 대역 검사로 제한한다. 가상 VPN 인터페이스에 iptables 규칙을 적용하는 기능은 별도 후속 작업이다.

## 5. 화면·명령어 계획

**1차는 설정 UI + 명확히 표시한 PING9 전용 접속 명령을 기본안**으로 한다. 기존 VyOS와 충돌하는 임의의 `set vpn ssl ...` 명령은 만들지 않는다. 서버 설정을 실제 VyOS 문법으로 제공하려면 별도 Task에서 OpenVPN 인터페이스·PKI 설정 중 지원할 부분을 확정하고 구현한다.

VyOS 1.4는 OpenVPN을 `set interfaces openvpn` 아래에서 설정한다. 이번 자체 모델과 실제 OpenVPN을 같은 구현이라고 부르지 않는다. 실제 VyOS 명령을 넣는다면 이름만 받아 성공시키지 말고 각 설정을 검사와 동작에 연결해야 한다.

| 위치 | 계획한 조작 | 결과 |
|---|---|---|
| Router 상세 | 서버 활성, listen 주소/포트, 풀·가상 IP, 허용 대역, 인증/신뢰 설정 | 일괄 검증 후 Document에 적용 |
| PC 상세 | 프로필 설정, 연결/해제, 상태·할당 IP·실패 사유 | Runtime 실행과 상태 표시 |
| 이벤트 패널 | 접속 요청, 신뢰/인증 확인, IP 할당, 데이터 전달·복원, 해제/만료 | 원인 장비·차단 규칙까지 추적 |
| 포트/주소 표시 | 가상 VPN 주소를 물리 주소와 별도로 표시 | 가상 포트를 케이블 연결 대상으로 노출하지 않음 |

**아래는 아직 없는 PING9 확장 명령의 제안이며, 실제 VyOS/Windows/Linux 기본 명령이 아니다.** 이름은 구현 Task에서 최종 고정하고 도움말에 PING9 전용임을 표시한다.

| 일반 형식 (제안) | 입력 예시 | 의미 |
|---|---|---|
| `vpn connect [프로필 이름]` | `vpn connect OFFICE` | 미리 설정한 프로필로 접속 |
| `vpn disconnect` | `vpn disconnect` | 연결 종료, 할당 주소·동적 경로 회수 |
| `vpn status` | `vpn status` | 접속 상태·가상 IP·카운터·사유 조회 |

`[프로필 이름]`은 대괄호 없이 `OFFICE` 같은 실제 값으로 바꾼다. 첫 범위에서는 PC당 저장 프로필 하나만 지원한다. 프로필 저장은 UI로 시작하며 실제 서버 설정 명령이라고 오해할 전체 CLI 예시는 구현·검증 후 실습안내서에 넣는다. PC의 기존 `ping`, OS별 `arp`, 파일 명령어, 폴더 프롬프트, Tab 후보는 보존한다.

## 6. 검증용 구성과 성공 기준

작은 구성부터 순차적으로 늘린다.

```text
A. PC_A ── R1 ── PC_B
B. PC_A ── ISP ── R1 ── PC_B
C. PC_A ── ISP ── FW1 ── R1 ── PC_B
```

최종 C 구성의 예시 주소:

| 구간 | 주소 |
|---|---|
| PC_A—ISP | PC_A 198.51.100.10/24, GW 198.51.100.1 / ISP 198.51.100.1/24 |
| ISP—FW1 | ISP 203.0.113.1/30 / FW1 203.0.113.2/30 |
| FW1—R1 | FW1 10.0.13.1/30 / R1 서버 물리 IP 10.0.13.2/30 |
| R1—PC_B | R1 192.168.2.1/24 / PC_B 192.168.2.10/24, GW 192.168.2.1 |
| VPN 가상망 | 172.20.0.0/29, 서버 172.20.0.1, 첫 PC 172.20.0.2 |
| 허용 대역 | 192.168.2.0/24 |

ISP에는 서버 endpoint까지의 `10.0.13.0/30 → 203.0.113.2` 경로만 추가한다. FW1은 기본 경로를 ISP 쪽으로, R1은 기본 경로를 FW1 쪽으로 둔다. ISP에는 내부망 `192.168.2.0/24`와 가상망 `172.20.0.0/29`의 경로를 추가하지 않는다. NAT 없이도 일반 라우팅으로 서버 물리 IP까지 도달하도록 한다. FW1의 요청·응답 허용 규칙을 별도로 준비한다.

- 미접속 상태에서는 내부망 ping 실패.
- connect 성공 시 가상 IP 할당, PC_A → PC_B ping 응답.
- PC_B → 할당 IP도 활성 세션의 역방향 정책 안에서 응답. 클라이언트 간 통신은 금지.
- 중간 ISP/FW에서 바깥 IP·TCP 포트를 확인. 터널 데이터 이벤트에만 안쪽 IP를 별도로 표시하고 일반 ICMP처럼 전달하지 않음.
- disconnect·만료·서버 중지 후 내부망 ping 실패, 동적 경로·주소 회수.
- 실제 암호화가 없으므로 trace 데이터 자체에는 안쪽 payload가 있을 수 있다. 관찰 화면과 저장 문서에서 실제 보호로 오해하지 않도록 구분한다.

## 7. 단계별 Task와 산출물

| 순서 / 제안 ID | 작업 | 완료 조건 |
|---|---|---|
| 0 / T15.3.1 | 교육용 범위·패킷/세션 계약, 타입·스키마·검증·상한 설계 | 옛 JSON 호환, 상태/경로/주소 규칙 명확화 |
| 1 / T15.3.2 | 바깥 교육용 TCP 헤더·라우터 전달·Firewall 포트 인식 | 실제 2홉 이상 경로와 양방향 포트 차단 테스트 |
| 2 / T15.3.3 | 서버/클라이언트 설정·접속 제어·신뢰/인증 검사·풀 할당 | 잘못된 인증·풀 고갈·timeout 시 잔여 상태 없음 |
| 3 / T15.3.4 | 데이터 감싸기/복원·split route·서버 반환 경로·해제 | A → B 구성에서 양방향 ping, 세션 우회 없음 |
| 4 / T15.3.5 | FW 포함 C 구성, 만료·장애·중복·설정 변경 | 실패 원인 trace, 세션/주소/경로 정리, 기존 VPN 회귀 |
| 5 / T15.3.6 | UI·확장 CLI·조회·이벤트·재생·실습안내서 | 일반 형식/실제 예시 제공, DEV 실습, 브라우저 확인 |
| 선택 / T15.3.7 | 실제 VyOS/OpenVPN 명령 subset과 매핑 | 공식 문법 대조 및 모든 지원 항목의 동작 테스트 |

커널/엔진 구현은 선영 담당 기본안으로 두되, 기존 Firewall·PC·화면 담당자와 변경 파일을 먼저 공유한다. 3인 분담을 할 경우 선영은 세션/터널/서버 라우팅, PC 담당은 클라이언트·CLI, 화면 담당은 설정·이벤트·안내 연결로 나눌 수 있다. **담당자 배정이 확정됐다는 뜻은 아니다.**

일정 추정: 기존 코드에 익숙한 1인 기준 **4~6 작업일**. 0~1단계 1~1.5일, 2단계 1일, 3~4단계 1.5~2일, 5단계 0.5~1.5일로 본다. 실제 TCP/TLS를 요구하면 이 추정은 적용하지 않는다. 첫 전송 실험이 끝나면 재산정한다. 날짜·마감·팀원 가용 시간은 아직 확정하지 않는다.

## 9. 착수 전 확인할 결정과 첫 작업

| 결정 | 추천 기본안 |
|---|---|
| 실제 암호화 수준 | 기존과 같은 교육 모델. 실제 TLS가 필요하면 별도 설계로 전환 |
| 게이트웨이 | 기존 Router 확장. Firewall을 VPN 서버로 겸용시키지 않음 |
| 화면/명령 | UI 설정 + PING9 확장 접속 명령. 실제 VyOS 문법 지원은 선택 후속 Task |
| 최초 데이터 | IPv4 ICMP, split tunnel, 서버 1개·PC당 세션 1개 |

**첫 구현은 T15.3.1~T15.3.2:** 작은 A 구성에서 바깥 교육용 TCP 메시지를 보내고, B/C로 늘려 라우터·Firewall이 실제로 전달/차단하는지 확인한다. 이 기반이 통과한 뒤에 인증·주소 할당·데이터 터널을 얹는다.
