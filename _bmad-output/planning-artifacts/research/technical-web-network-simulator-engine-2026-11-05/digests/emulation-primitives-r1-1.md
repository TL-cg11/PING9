## Findings

### Q1. Network namespaces, veth, bridge: privileges and hosting

1. Creating any non-user namespace (which includes network namespaces) requires CAP_SYS_ADMIN, but only "in the caller's user namespace"; the page states the rule generically and does not name CLONE_NEWNET. | https://man7.org/linux/man-pages/man7/user_namespaces.7.html | man7.org / Linux man-pages project (man-pages 6.19) | 2026-02-08 | accessed 2026-11-05 | high | capability
2. Rootless creation is possible in principle: "Since Linux 3.8, unprivileged processes can create user namespaces", and a process in a new user namespace "starts out with a complete set of capabilities" there, while holding none in the parent namespace. | same URL | man7.org / Linux man-pages project | 2026-02-08 | accessed 2026-11-05 | high | capability
3. Privileged operations on a non-user namespace's resources are checked against the user namespace that owns it. Inference (mine, not stated on the page): a topology of netns + veth + bridge built entirely inside one unprivileged user namespace needs no host root, but it cannot touch host-owned interfaces or bridges. | same URL | man7.org / Linux man-pages project | 2026-02-08 | accessed 2026-11-05 | medium (rule is high; the veth/bridge application is inference) | capability
4. Documented limits on that page: kernel must be built with CONFIG_USER_NS; user namespaces nest at most 32 levels (EUSERS beyond that). The page does not cover distro-level switches. | same URL | man7.org / Linux man-pages project | 2026-02-08 | accessed 2026-11-05 | high | capability
5. Snippet-only: CVE-2026-31692 — rtnl_newlink() lacked a CAP_NET_ADMIN check on the peer namespace for paired devices (veth, vxcan, netkit), letting an unprivileged user with a user namespace create interfaces in arbitrary network namespaces including init_net. Fixed-version list (6.18.24, 6.19.14, 7.0 reported unaffected) came from an aggregator and was hard to parse. Relevant if students ever get shell-level access on a shared kernel. | https://nvd.nist.gov/vuln/detail/CVE-2026-31692 (also stack.watch, Oracle, Bell-SW listings) | NVD / NIST | 2026 (exact date not retrieved) | accessed 2026-11-05 | medium for existence, low for affected versions | security
6. Snippet-only: in an unprivileged LXC container, `ip netns add` failed with "mount --make-shared /var/run/netns failed: Permission denied", and `security.nesting=true` did not fix it for the reporter. Indicates `ip netns` (which bind-mounts under /run/netns) can fail even where raw namespace creation is allowed. | https://discuss.linuxcontainers.org/t/3-0-1-adding-network-namespace-in-unpriviliged-container/2238 | Linux Containers forum (user report) | undated in snippet (LXD 3.0.1 era, old) | accessed 2026-11-05 | low | capability
7. Snippet-only, PaaS: a Fly.io community thread states each app container runs in its own VM, so normal VM-style privilege setup works inside it; there is no Docker-style `--cap-add` knob. A Railway feedback post requests NET_ADMIN / /dev/net/tun, implying Railway does not grant it; the same post claims NET_ADMIN is available on Fly.io, AWS ECS and Cloud Run, which is one user's assertion. | https://community.fly.io/t/feature-request-set-cap-net-admin/3074 ; https://station.railway.com/feedback/request-dev-net-tun-or-net-admin-capab-a9470a3f | Fly.io community forum ; Railway feedback board | undated in snippets | accessed 2026-11-05 | low | capability
